@CARD hw2.preflight | Preflight：initramfs、LUKS、預設 target
A> HW2 的 VM 是一台「故意被弄壞的車」：開機零件（initramfs）被藏在 /root、預設停在維修模式（rescue）。修車原則：不重灌、不 mkfs，用學過的開機知識一層層修。
B> 開機問題：**initramfs** 映像放在 /root，需找出並放回 /boot（對應 kernel 版本），必要時 update-initramfs / 修 GRUB
B> 開機後落在 **rescue mode** → 檢查並修正預設 target：**systemctl get-default**、**systemctl set-default multi-user.target**
B> **LUKS / dm-crypt** 磁碟加密：預設密碼 judge 改為 ilovesa2026 → **cryptsetup luksChangeKey <device>**（或 luksAddKey 再 luksKillSlot）
B> **禁止重灌或對任何分割區 mkfs**；要以 **UEFI 模式**開機
B> 也要維持 HW0：sudo NOPASSWD、wireguard、ssh key、hostname
?cmd 把系統預設開機 target 改回 multi-user.target：
= systemctl set-default multi-user.target
= systemctl set-default multi-user
E> get-default 查詢、set-default 設定。
?cmd 變更 LUKS 裝置 /dev/sda3 的解鎖密碼：
= cryptsetup luksChangeKey /dev/sda3
E> 會要求輸入舊密碼與新密碼。
?mc 開機時要求輸入 LUKS 密碼這一步，是在哪個階段由誰負責？
+ initramfs（early user space）解鎖加密裝置，之後才掛載 root
- BIOS 在 GRUB 載入 kernel 之前就解鎖加密裝置
- systemd 進入 multi-user.target 之後才解鎖
- GRUB 載入 kernel 後，由 kernel 自己解鎖，再交給 initramfs 掛載
E> root 在加密裝置上時，解鎖一定要在掛載 root 之前。

@CARD hw2.snapper | SnApper：Btrfs 快照管理腳本
A> SnApper 是自己寫的「相機管家」：snapshot 拍照（唯讀、自動輪替只留 N 張）、list 列相簿、delete 刪照片、rollback 把照片「沖洗成可用的新版本」換回原處，而且照片本身要留著。
B> 指令：SnApper snapshot SUBVOL [-c ROTATION_COUNT]、list [-p SUBVOL] [-i ID]、delete [ID]、rollback ID；放在 **$PATH** 中
B> snapshot 放在 <ROOT_VOLUME>/snapshot/<SUBVOL>/**@YYYYMMDD-hhmmss**，直接在 root volume（ID 5）下，**唯讀**；輸出 Snap '<PATH>' [<ID>]
B> 輪替：超過 ROTATION_COUNT（預設 5）就刪除 **subvolume ID 最小**的，直到 ≤ count
B> list 欄位 ID SUBVOLUME TIME，**不能用 TAB** 分隔；-p、-i 可同時使用
B> rollback：snapshot 仍存在、subvolume 可寫、remount 後持續（作法：對唯讀 snapshot 建立可寫 snapshot 取代原 subvolume）
X> date +%Y%m%d-%H%M%S        # 20251003-163650
X> btrfs subvolume snapshot -r /mnt/hw2root/pool1 /mnt/hw2root/snapshot/pool1/@$(date +%Y%m%d-%H%M%S)
X> btrfs subvolume list -p -a -t /mnt/hw2
?fill 產生 20251003-163650 這種格式的 date 指令格式字串是 date +＿＿
= %Y%m%d-%H%M%S
E> %Y 年、%m 月、%d 日、%H 時、%M 分、%S 秒。
?mc SnApper 預設保留 5 個 snapshot，建立第 6 個之後要刪掉哪一個？
+ ID 最小的
- 最新建立的那個
- 隨機一個
- 全部刪掉重來
E> subvolume ID 最小的那個（最舊）規格：delete snapshot with smallest subvolume ID，重複直到 ≤ ROTATION_COUNT。
?cmd 刪除路徑為 /mnt/root5/snapshot/pool1/@20251003-163650 的 snapshot：
= btrfs subvolume delete /mnt/root5/snapshot/pool1/@20251003-163650
= btrfs sub delete /mnt/root5/snapshot/pool1/@20251003-163650
E> snapshot 是 subvolume，用 subvolume delete。

@CARD hw2.sshd | 修正 SSH 設定（sshd_config）
A> sshd_config 是 SSH 大門的「門禁規則表」。改完一定先 sshd -t 檢查文法，再 reload；並保持一個已登入的視窗，免得把自己鎖在門外。
B> 只聽 **Port 22**；**PermitRootLogin no**
B> 不要 banner：**Banner none**（不可修改或刪除 /etc/ssh/banner.txt）
B> 不要 uname 輸出：Debian 的 motd 由 /etc/update-motd.d/（如 10-uname）產生 → 移除其執行權限
B> 要 Last login 訊息：**PrintLastLog yes**
B> 檢查 sshd -t；重載 systemctl reload ssh；sshd_config.d/ 的 Include 與 Match 區塊也會影響
?mt 配對 sshd_config 設定：
> PermitRootLogin no :: 禁止 root 直接 SSH 登入
> Banner none :: 不顯示登入前的 banner
> PrintLastLog yes :: 顯示 Last login 訊息
> Port 22 :: 只監聽 22 port
E> 改完 sshd -t 再 reload。
?mc HW2 要求登入時「不要顯示 banner」，但又規定不能修改或刪除 /etc/ssh/banner.txt。應該怎麼做？
+ 在 sshd_config 設定 Banner none
- 把 banner.txt 的內容清空，檔案本身保留
- 把 banner.txt 改名，sshd 找不到就不會顯示
- 把 sshd 換成 telnet，就不會有 banner 機制
E> 題目禁止動檔案，所以從設定關掉。
?cmd 修改 sshd 設定後，不中斷現有連線地重新載入（Debian 的服務名稱是 ssh）：
= systemctl reload ssh
= sudo systemctl reload ssh
= systemctl reload ssh.service
= systemctl reload sshd
E> reload 前先用 sshd -t 檢查語法。

@CARD hw2.sftp | SFTP chroot 與 internal-sftp
A> chroot 是「把客人關在指定的展示間裡」：他以為展示間就是整棟樓的 /。sshd 有嚴格規定：展示間（以及往上每一層路徑）必須是 root 擁有、而且別人不能寫，不然 sshd 拒絕 chroot。internal-sftp 是 sshd 內建的 SFTP 服務，不需要 chroot 裡面有任何程式。
B> **Subsystem sftp internal-sftp**（內建 sftp server，chroot 內不需要 binary）
B> 用 **Match User / Match Group** 對特定使用者套用：**ChrootDirectory**、**ForceCommand internal-sftp**（只能 SFTP，不能 SSH shell）、可關閉 forwarding
B> **ChrootDirectory 的路徑每一層都必須是 root 擁有，且 group/other 不可寫**
B> 管理員（sysadm）**不 chroot**；所有人的 SFTP 起始目錄都在 $SFTP_ROOT（internal-sftp **-d** 設定起始目錄）
B> 上傳檔案移除 other 的 rwx：internal-sftp **-u 0007**（強制 umask）
B> 公鑰登入：每個帳號的 ~/.ssh/authorized_keys
X> Match User sftp-u1,sftp-u2,anonymous
X>     ChrootDirectory /mnt/hw2/sftp
X>     ForceCommand internal-sftp -u 0007
X>     AllowTcpForwarding no
?mc 設定 ChrootDirectory /mnt/hw2/sftp 後 SFTP 一登入就斷線，log 顯示 bad ownership or modes for chroot directory。原因？
+ chroot 路徑的擁有者或權限不對
- 使用者沒有 shell
- internal-sftp 沒有安裝
- 防火牆擋住 22 port
E> chroot 路徑上的某一層目錄不是 root 擁有，或 group/other 可寫。sshd 要求 chroot 目錄與其所有上層都 root 擁有且不可被他人寫入。
?mt 配對 sshd_config 指令：
> ChrootDirectory :: 把使用者限制在指定目錄當作 /
> ForceCommand internal-sftp :: 只允許 SFTP，不允許 shell
> Match Group :: 只對特定群組套用後面的設定
> internal-sftp -u 0007 :: 強制上傳檔案的 umask
E> Match 區塊一直作用到下一個 Match 或檔案結尾。
?tf 使用 internal-sftp 時，chroot 目錄內必須放一份 sftp-server 程式。
=F
E> internal-sftp 是 sshd 內建，這正是用它搭配 chroot 的原因。

@CARD hw2.sftpperm | SFTP 權限設計（public / private / hidden）
A> 用權限位元蓋一座「藏寶屋」：public/ 是大家都能放東西的公共區，但只能拿走自己的（sticky）；private/ 是「看不到房間清單、但知道名字就能走進去」（只給 x 不給 r），hidden/treasure 就是知道地址才拿得到的寶藏。
B> public/：registered user 可 get/put/mkdir，只能刪除**自己的**檔案 → **sticky bit** + 群組可寫；anonymous 唯讀 → 不在可寫群組
B> 管理員 sysadm 可刪除全部：讓 sysadm 成為目錄**擁有者**（sticky 允許目錄擁有者刪除）
B> private/：使用者**不能 ls**、**不能寫**、**能 cd**、能 get hidden/treasure → 目錄只給 **x**（--x）、treasure 給 r
B> 新目錄自動屬於共同群組 → **setgid** 目錄
B> 上傳檔移除 other 的 rwx → umask 007 或預設 ACL 的 o::---；但 anonymous 對檔案而言就是 other，所以要另外用 **ACL（u:anonymous:r）** 給它讀取權（見「umask 007 與 anonymous 唯讀的衝突」）
?mc 要讓使用者「可以 cd 進 private/、可以下載已知名稱的檔案，但不能 ls 列出內容」，private/ 對他們應給什麼權限？
+ 只給 x（執行/通過），不給 r
- 只給 r，不給 x
- 給 rw，不給 x
- 給 rwx 加 sticky
E> 目錄 r = 列出、x = 通過。
?mc public/ 中「使用者只能刪除自己上傳的檔案」，關鍵的權限位元是？
+ sticky bit
- setuid
- setgid
- 檔案本身的 w
E> sticky 目錄只允許檔案擁有者、目錄擁有者或 root 刪除 / 改名。

@CARD hw2.log | SFTP logging：journald + rsyslog
A> 讓 SFTP 的 log「獨立成一本帳」：先讓 internal-sftp / sftp-server 會寫 log（-l INFO -f 設施），再用 rsyslog 的過濾規則依程式名稱挑出來寫進 /var/log/sftp.log，並且「stop」避免混到其他 log。chroot 中的使用者還需要讓 /dev/log 在 chroot 裡可用，log 才送得出來。
B> internal-sftp / sftp-server 開 log：**-l INFO**（log level）、**-f AUTH / LOCAL*n***（facility）
B> 查 log：**journalctl -t internal-sftp -t sftp-server**（-t 依 syslog identifier 過濾）
B> rsyslog 依 **programname** 過濾寫到 /var/log/sftp.log，再 **stop** 避免寫進其他檔
B> chroot 使用者：需在 chroot 內提供 /dev/log（例如 rsyslog 增加 socket、或 bind mount）
B> 檔名要排在 50-default.conf 之前（例如 10-sftp.conf），stop 才能避免訊息又寫進 auth.log
X> # /etc/rsyslog.d/10-sftp.conf
X> if $programname == 'internal-sftp' or $programname == 'sftp-server' then {
X>     action(type="omfile" file="/var/log/sftp.log")
X>     stop
X> }
?cmd 用 journalctl 只看 syslog identifier 為 internal-sftp 與 sftp-server 的 log：
= journalctl -t internal-sftp -t sftp-server
= journalctl -t sftp-server -t internal-sftp
E> -t = SYSLOG_IDENTIFIER。
?mc rsyslog 規則寫完 action 後加 stop 的目的？
+ 不讓後面的規則再處理它
- 停止 rsyslog daemon
- 停止 SFTP 服務
- 讓 log 只寫一次就關檔
E> 讓符合的訊息不再被後面的規則處理（不會混進 /var/log/syslog 等）規格要求 sftp.log 是純 SFTP log，同時其他檔不該混入。

@CARD hw2.watchd | sftp_watchd：監控上傳並做成 systemd service
A> sftp_watchd 是「上傳檢查站的保全」：盯著每個新上傳的檔案，看前 4 個 bytes 是不是 ELF 的身分證（\x7fELF），或 MD5 是否在黑名單上；違規就移到 .violated/ 並寫 log。再把保全登記成 systemd service，讓 systemctl 能叫他上班、下班、看狀態，journalctl -u 能看他的值勤紀錄。
B> 偵測：**ELF** 檔（只看前 4 bytes：**0x7F 'E' 'L' 'F'**）、**MD5** 在禁止清單中（md5sum）
B> 違規 → 移到 ${SFTP_ROOT}/private/.violated/ 並記錄指定格式的 log
B> 監看檔案事件：如 **inotifywait -m -r -e close_write**
B> 寫成 systemd service：/etc/systemd/system/sftp_watchd.service → daemon-reload → enable --now；支援 start/stop/status/restart；log 用 **journalctl -u sftp_watchd**（印到 stdout/stderr 就會進 journal）
X> [Unit]
X> Description=SFTP upload watcher
X> After=network.target
X> [Service]
X> ExecStart=/usr/local/bin/sftp_watchd
X> Restart=on-failure
X> [Install]
X> WantedBy=multi-user.target
?mc 判斷檔案是不是 ELF 執行檔，只看前 4 bytes 應該是？
+ 0x7F 45 4C 46（\x7fELF）
- 23 21 2F 62（#!/b）
- 4D 5A 90 00（MZ，Linux 執行檔）
- 50 4B 03 04（PK）
E> MZ 是 Windows PE、#! 是 script、PK 是 zip。
?mt 配對 service unit 的 section：
> [Unit] :: 描述與依賴 / 順序（Description、After）
> [Service] :: 如何執行（ExecStart、Restart）
> [Install] :: enable 時掛到哪個 target（WantedBy）
E> 沒有 [Install] 就不能 enable。
?cmd 讓 sftp_watchd.service 立即啟動並在開機時自動啟動：
= systemctl enable --now sftp_watchd
= systemctl enable --now sftp_watchd.service
E> 新寫的 unit 記得先 daemon-reload。
?cmd 計算 upload.bin 的 MD5：
= md5sum upload.bin
E> FreeBSD 上是 md5。

@CARD hw2.p_plan | HW2 作戰順序與存檔點
A> HW2 像一款「不能讀檔重來」的遊戲：judge 甚至可能 dd 掉你的磁碟。所以每完成一個階段就在 VM 存一次檔（快照），並且每一關都問自己：重開機之後它還在嗎？
B> 順序：Preflight（能開機、解鎖、進 multi-user）→ 2-1 縮 root、new-part → 加磁碟、RAID10、Btrfs、subvolume、fstab → SnApper → 2-2 sshd、帳號、SFTP 權限 → 2-3 logging、sftp_watchd
B> 每一階段結束：**VM 快照**＋**重開機驗證**；作業規格明寫「Make sure everything works after reboot」
B> 持久化清單：fstab（掛載）、systemctl enable（服務）、set-default（target）、crypttab 與 initramfs（解鎖）、hostnamectl
B> judge 從 `$(which SnApper)`、`$(which sftp_watchd)` 拿腳本：要在 PATH、judge 讀得到，而且**不能呼叫你自己寫的其他腳本或程式**
B> 同時維持 HW0：sudo NOPASSWD、WireGuard、SSH key、hostname
?mc 規格要求所有設定在重開機後仍然有效。下列哪一項「不會」自動在重開機後保留？
+ 只用 mount 指令手動掛上、沒有寫進 fstab 的掛載
- systemctl enable 過的服務
- set-default 設定的 target
- hostnamectl set-hostname 設定的名稱
E> 手動 mount 只存在於這次開機。
?tf SnApper 腳本可以把共用函式寫在另一個 /usr/local/lib/snap_lib.sh，再用 source 載入。
=F
E> 規格：腳本不得呼叫任何其他自寫的 script 或執行檔；全部寫在同一個檔案裡。

@CARD hw2.p_preflight | Preflight 實戰：從開不了機到登入
A> Preflight 是三道關卡串在一起：GRUB 找不到 initramfs（開不了機）→ 解鎖 LUKS → 一進系統就掉進 rescue。每一道都對應到開機流程的一層，照順序一關一關打。
B> 關卡一：開機卡在 kernel panic 或找不到 root → initramfs 不在 /boot。在 GRUB 按 **c** 用 `ls` 看分割區、或用 rescue / Live 環境把 /root 底下的 initrd 放回 /boot（版本與 vmlinuz 一致），再 `update-grub`
B> 臨時開機也可以在 GRUB 指令列手動下：`linux /vmlinuz-版本 root=...`、`initrd /initrd.img-版本`、`boot`（路徑依 /boot 是否獨立分割而不同）
B> 關卡二：解鎖密碼 judge → 進系統後 `cryptsetup luksChangeKey` 換成 ilovesa2026，**重開機實測**新密碼
B> 關卡三：每次都進 rescue → `systemctl get-default`、`cat /proc/cmdline`、`/etc/default/grub` 三處都查
B> 用 **find / -name 'initrd*' 2>/dev/null** 找出被藏起來的檔案；用 `uname -r` 對版本
B> 還要確認 UEFI 模式開機：存在 **/sys/firmware/efi** 目錄就是 UEFI
X> ls /sys/firmware/efi && echo "UEFI"
X> find / -name 'initrd.img*' 2>/dev/null
X> cp /root/initrd.img-$(uname -r) /boot/ && update-grub
?cmd 檢查系統是否以 UEFI 模式開機（判斷 /sys/firmware/efi 是否存在）：
= ls /sys/firmware/efi
= test -d /sys/firmware/efi
= [ -d /sys/firmware/efi ]
= ls -d /sys/firmware/efi
E> 以 legacy BIOS 開機時沒有這個目錄。
?mt 配對 Preflight 的症狀與對應的處理：
> 開機時 VFS: Unable to mount root fs :: 把 initramfs 放回 /boot 並 update-grub
> 一進系統就是 rescue mode :: systemctl set-default multi-user.target 並檢查 kernel 參數
> 要求的磁碟密碼是 judge :: cryptsetup luksChangeKey 換成新密碼
> 開機後 sudo 要輸入密碼 :: 用 visudo 設定 NOPASSWD
E> 每一關對應開機流程的不同層。
?fill 在 GRUB 選單按 ＿ 可以進入 GRUB 指令列，手動下 linux、initrd、boot 指令
= c
E> 按 e 則是編輯目前選中的那一筆。

@CARD hw2.p_layout | 2-1 實戰：Btrfs 子卷與掛載配置
A> 這一關的要點是「所有房間都直接開在大廳旁邊」：root、sftp、pool1、pool2 四個 subvolume 都直接在 ID 5 底下，snapshot/ 只是一般目錄。但掛載的時候，sftp、pool1、pool2 要掛在 root 的「裡面」，所以 root 裡要先有這三個空目錄當掛載點。
B> 在 top-level 建 4 個 subvolume 與 snapshot/{sftp,pool1,pool2} 三個**目錄**
B> 先把 root 掛到 /mnt/hw2，再在 /mnt/hw2 裡 `mkdir sftp pool1 pool2`（這些是 root subvolume 裡的普通目錄，當作掛載點，**不是**巢狀 subvolume）
B> fstab 四行，來源都寫 **/dev/mapper/SA2026vg-SARaid10**，選項用 **subvol=名稱**；/mnt/hw2 那行要排在前面
B> 驗證：`btrfs subvolume list -p -a -t /mnt/hw2` 每個的 parent 與 top level 都是 5；`findmnt -t btrfs` 看到四個掛載；`btrfs filesystem show` 確認 Label 是 SAHW2
X> mount -o subvol=root /dev/mapper/SA2026vg-SARaid10 /mnt/hw2
X> mkdir /mnt/hw2/{sftp,pool1,pool2}
X> # /etc/fstab
X> /dev/mapper/SA2026vg-SARaid10 /mnt/hw2       btrfs subvol=root  0 0
X> /dev/mapper/SA2026vg-SARaid10 /mnt/hw2/sftp  btrfs subvol=sftp  0 0
X> /dev/mapper/SA2026vg-SARaid10 /mnt/hw2/pool1 btrfs subvol=pool1 0 0
X> /dev/mapper/SA2026vg-SARaid10 /mnt/hw2/pool2 btrfs subvol=pool2 0 0
?mc 在掛著 root subvolume 的 /mnt/hw2 裡執行 `btrfs subvolume create /mnt/hw2/pool1`，會有什麼問題？
+ pool1 變成 root 底下的巢狀子卷
- 指令會失敗，因為 /mnt/hw2 是唯讀
- 沒有問題，結果和在 top-level 建立相同
- pool1 會變成 snapshot
E> pool1 會變成 root 底下的巢狀 subvolume，違反「所有 subvolume 都直接在 ID 5 底下」。subvolume 要在 top-level（例如 /mnt/root5）底下建立；/mnt/hw2/pool1 只要是普通目錄當掛載點。
?tf /mnt/hw2/sftp 這個掛載點目錄，本身必須是一個 Btrfs subvolume。
=F

B> 之後：**lvcreate -l 100%FREE -n new-part debian-vg** → **mkfs.ext4** → fstab（UUID 或 /dev/mapper/debian--vg-new--part）→ **mount -a**、**findmnt --verify**

X> cryptsetup open /dev/sda3 cryptroot
X> vgchange -ay
X> e2fsck -f /dev/debian-vg/root
X> lvreduce --resizefs -L 15G /dev/debian-vg/root
X> # 回到系統後
X> lvcreate -l 100%FREE -n new-part debian-vg
X> mkfs.ext4 /dev/debian-vg/new-part
X> echo '/dev/mapper/debian--vg-new--part /mnt/new-part ext4 defaults 0 2' >> /etc/fstab
?mc 為什麼縮小 root LV 要從 Live 環境操作？
+ ext4 不支援線上縮小，而 root 在系統執行時一定是掛載狀態
- lvreduce 這個工具只存在於 Live ISO 中
- 執行中的系統會鎖住 LUKS header，lvreduce 無法更新
- root LV 在系統執行時是唯讀的
E> ext4 可以線上放大（resize2fs 在掛載時也能擴大），但縮小必須卸載。
?fill VG debian-vg 的 LV new-part，在 /dev/mapper 底下的名稱是 /dev/mapper/＿＿
= debian--vg-new--part
E> device mapper 用單一 - 分隔 VG 與 LV，所以名稱中原本的 - 都會變成 --。
?ord 縮小 LV（手動、不用 --resizefs）的正確順序：
> 卸載檔案系統並 e2fsck -f
> resize2fs 把檔案系統縮到比目標小
> lvreduce 把 LV 縮到目標大小
> resize2fs 不帶大小，讓檔案系統撐滿 LV
E> 如果先縮 LV，檔案系統尾端的資料會被切掉。
?cmd 在 Live 環境把 debian-vg/root 連同檔案系統一起縮到 15G（一個指令）：

= lvreduce -r -L 15G /dev/debian-vg/root
= lvreduce --resizefs -L 15G debian-vg/root
= lvreduce -r -L 15G debian-vg/root
= lvresize --resizefs -L 15G /dev/debian-vg/root
= lvresize -r -L 15G /dev/debian-vg/root
E> -r（--resizefs）會先呼叫 fsadm/resize2fs 縮檔案系統，再縮 LV，順序由工具保證。

B> 觀察：**lvs -a -o name,segtype,copy_percent,devices SA2026vg**（看到 rimage / rmeta 子 LV、同步進度 Cpy%Sync）

X> sudo vgcreate SA2026vg /dev/sdb1 /dev/sdb2 /dev/sdb3 /dev/sdb4
X> sudo lvcreate --type raid10 -m 1 -i 2 -l 100%FREE -n SARaid10 SA2026vg
X> sudo lvs -a -o name,segtype,copy_percent,devices SA2026vg

- 2
- 3
- 8

X> /dev/mapper/SA2026vg-SARaid10  /mnt/hw2/sftp   btrfs  subvol=sftp   0 0

@CARD hw2.p_rollback | 2-1 實戰：SnApper rollback 的原理
A> rollback 不是「把照片貼回去」，而是「用照片洗出一份新的、可以寫的副本，換掉原本的房間」。照片（唯讀 snapshot）留著，舊房間刪掉，新房間取原本的名字，fstab 依名字掛，所以重新掛載後看到的就是回滾後的內容。
B> 從 ID 找 snapshot 路徑：snapshot/**<SUBVOL>**/@時間 → 由路徑**自動推出 SUBVOL**
B> 步驟：掛 top-level（**subvolid=5**）→ **umount /mnt/hw2/<SUBVOL>** → 舊子卷**改名**（mv 子卷目錄）→ **btrfs subvolume snapshot 唯讀快照 <top>/<SUBVOL>**（不加 -r → 可寫）→ 刪掉舊子卷 → **mount /mnt/hw2/<SUBVOL>**（依 fstab 的 subvol= 名稱）
B> 要求：**snapshot 仍存在**、子卷**可寫**、**umount / remount 後仍是回滾後的狀態**
B> 子卷正在使用（SFTP 連線、sftp_watchd 監看）→ umount 會 **target is busy**：先 **fuser -vm** 找出 process，必要時暫停服務
B> 驗證：**btrfs property get -ts <子卷> ro** 應為 false；touch 測試可寫
X> mount -o subvolid=5 /dev/mapper/SA2026vg-SARaid10 /mnt/root5
X> umount /mnt/hw2/pool2
X> mv /mnt/root5/pool2 /mnt/root5/pool2.old
X> btrfs subvolume snapshot /mnt/root5/snapshot/pool2/@20251003-194529 /mnt/root5/pool2
X> btrfs subvolume delete /mnt/root5/pool2.old
X> mount /mnt/hw2/pool2
?mc rollback 時用 btrfs subvolume snapshot（不加 -r）從唯讀快照建立新子卷，目的是？
+ 讓回滾後的子卷可寫，同時保留原本的唯讀快照
- 讓新的子卷也維持唯讀，避免回滾後又被改壞
- 新子卷建立後會自動取代原本的快照
- 加快建立 snapshot 的速度
E> 規格要求 snapshot 仍存在、subvolume 可寫。
?cmd 檢查子卷 /mnt/root5/pool2 是否為唯讀：
= btrfs property get -ts /mnt/root5/pool2 ro
= btrfs property get /mnt/root5/pool2 ro
= sudo btrfs property get -ts /mnt/root5/pool2 ro
E> 輸出 ro=true 或 ro=false。
?mc rollback 時 umount /mnt/hw2/sftp 出現 target is busy，第一步該做什麼？
+ 用 fuser -vm 找出佔用者
- 直接 reboot
- 用 mkfs 重建
- 把 sftp 從 fstab 刪掉
E> fuser -vm /mnt/hw2/sftp（或 lsof）找出佔用的 process。常見是 sftp_watchd 或還沒結束的 sftp session。
?sa 請說明 Btrfs 中「唯讀快照」如何用來實作 rollback，並解釋為什麼 fstab 應該用 subvol=名稱 而不是 subvolid= 掛載。
R> Btrfs 的 snapshot 本身也是一個 subvolume，以 copy-on-write 方式共享資料，建立時幾乎不佔空間。唯讀快照用來保存某個時間點的狀態，不會被意外修改。
R> rollback 時不能直接把唯讀快照拿來用（它不可寫，也要保留），所以對它再做一次「可寫的 snapshot」，得到一份內容相同、可寫的新 subvolume；把原本的 subvolume 改名或刪除，新 subvolume 取原本的名稱放在同一個位置（top-level 下），再重新掛載。
R> 新 subvolume 的 ID 和原本不同。若 fstab 寫 subvolid=，重新掛載時會找不到（舊的已刪）或掛到舊的；寫 subvol=名稱 則依路徑名稱尋找，自動掛到新建的那個，達成「umount/remount 後仍維持回滾狀態」。
P> snapshot 是 CoW 的 subvolume
P> 從唯讀快照建立可寫快照，取代原 subvolume 名稱
P> 原快照保留
P> 新 subvolume ID 不同，所以 fstab 要依名稱掛載

@CARD hw2.p_snapcli | 2-1 實戰：SnApper 的參數解析與輸出格式
A> 評分程式會一字一字比對輸出，所以 SnApper 的「外觀」跟功能一樣重要：help 文字、Snap / Destroy ID / Rollback 這幾行的格式、list 的欄位，都要跟規格完全一樣；錯誤訊息則印到 stderr，exit code 非 0。

B> 成功輸出：**Snap '<SNAPSHOT_PATH>' [<ID>]**、**Destroy ID <ID>**（刪全部時每個一行）、**Rollback '<SNAPSHOT_PATH>' [<ID>] to <SUBVOL>**

X> cmd=$1; shift
X> case $cmd in
X>   snapshot) sub=$1; shift; count=5
X>             while getopts c: opt; do case $opt in c) count=$OPTARG;; *) usage >&2; exit 1;; esac; done ;;
X>   list)     while getopts p:i: opt; do case $opt in p) fp=$OPTARG;; i) fi=$OPTARG;; esac; done ;;
X>   -h|'')    usage; exit 0 ;;
X> esac
X> printf '%-5s %-10s %s\n' ID SUBVOLUME TIME

- getopts 只能處理一個選項
- shift 會自動解析 -c
- 不 shift 的話 -c 會被當成檔名刪除
E> getopts 從 $1 開始解析，遇到第一個非選項參數就停止，所以要先移除子指令與 SUBVOL。getopts 解析的是「目前的」位置參數。

?mc SnApper list 用 printf '%s\t%s\t%s\n' 輸出，評分會出什麼問題？
+ 規格禁止用 TAB 分隔欄位，應改用空白對齊
- printf 不能用 %s 印出數字
- \n 在 bash 的 printf 中無效
- 每次呼叫都會多印一行標頭
E> 用 SnApper list | cat -A 檢查，TAB 會顯示成 ^I。
?tf SnApper 的錯誤訊息印到 stdout 也沒關係，只要 exit code 是 0。
=F
E> 慣例：錯誤印到 stderr，失敗時 exit code 非 0，評分程式和使用者才分得出成功與失敗。

@CARD hw2.p_users | 2-2 實戰：建立 SFTP 帳號與金鑰

@CARD hw2.p_matchcfg | 2-2 實戰：sshd 的 Match 設定與起始目錄
A> sshd_config 用 Match 區塊替「某些人」換一套規則。會員和訪客：被 chroot、強制只能用 internal-sftp、起始目錄是 /（在 chroot 裡就是 $SFTP_ROOT）。館長 sysadm 不 chroot，走一般的 Subsystem，但起始目錄也指向 $SFTP_ROOT。這也解釋了規格裡 log 為什麼同時有 internal-sftp 與 sftp-server 兩種名字。
B> chroot 使用者：**Match Group sftponly** → **ChrootDirectory /mnt/hw2/sftp**、**ForceCommand internal-sftp -d / -u 0007 -l INFO**、AllowTcpForwarding no、X11Forwarding no、PermitTTY no
B> **-d /**：chroot 後的起始目錄（chroot 內的 / = $SFTP_ROOT）
B> sysadm：**Subsystem sftp /usr/lib/openssh/sftp-server -d /mnt/hw2/sftp -l INFO -u 0007** → log 名稱是 **sftp-server**；chroot 使用者的 log 名稱是 **internal-sftp**
B> **Match 一直到下一個 Match 或檔案結尾**：Match 放在檔案最後面
B> 陷阱：Debian 主檔開頭有 **Include /etc/ssh/sshd_config.d/*.conf**，若在被 include 的檔案寫 Match，主檔後面所有設定都會被吞進那個 Match
B> ChrootDirectory 每一層（/、/mnt、/mnt/hw2、/mnt/hw2/sftp）都必須 **root 擁有、group/other 不可寫**
X> Subsystem sftp /usr/lib/openssh/sftp-server -d /mnt/hw2/sftp -l INFO -u 0007
X> Match Group sftponly
X>     ChrootDirectory /mnt/hw2/sftp
X>     ForceCommand internal-sftp -d / -u 0007 -l INFO
X>     AllowTcpForwarding no
X>     X11Forwarding no
X>     PermitTTY no
?mc 規格範例 log 中 sysadm 的紀錄是 sftp-server[1979]，sftp-u1 卻是 internal-sftp[2029]。原因？
+ 兩者使用的 SFTP 實作不同
- 兩個使用者連到不同的 sshd
- sftp-u1 使用了比較新的 SFTP 協定
- 這是 rsyslog 改名的結果
E> sysadm 走 Subsystem 的 sftp-server 程式；chroot 使用者被 ForceCommand internal-sftp 使用 sshd 內建的 SFTP。journalctl -t internal-sftp -t sftp-server 兩個識別字都要查，才能看到所有使用者的紀錄。
?mc 在 /etc/ssh/sshd_config.d/sftp.conf 寫了 Match Group sftponly 區塊，結果 PasswordAuthentication no 等全域設定好像只對 sftponly 生效。原因？

- 被 include 的檔名必須以數字開頭（如 00-sftp.conf）才會照順序生效
- Match 的變更只有 restart 才生效，reload 只會重新讀取全域設定
E> 把 Match 寫在主檔最後，或確保 include 的檔案只放全域設定。

@CARD hw2.p_acldesign | 2-2 實戰：umask 007 與 anonymous 唯讀的衝突
A> 規格有兩個看起來打架的要求：「上傳的檔案要拿掉 other 的所有權限」，以及「anonymous 要能讀 public 裡的檔案」。anonymous 不在會員群組裡，對檔案來說它就是 other，other 沒權限它就讀不到。解法是 ACL：給 anonymous 一個「具名讀取權」，它就不必靠 other 位元。
B> 上傳檔案 other 為 ---（umask 007 或預設 ACL 的 **o::---**）→ anonymous（屬於 other）**讀不到**
B> 解法：在 public 設 **預設 ACL**：**d:u:anonymous:r-x**、d:u:sysadm:rwx、**d:o::---**；新建的檔案、目錄自動繼承
B> 有預設 ACL 的目錄裡，新檔權限由預設 ACL 決定、**不套用 umask**；要確認 **mask** 沒把 anonymous 的 r 截掉
B> 已存在的內容用 **setfacl -R -m** 補上（預設 ACL 只影響之後建立的）
B> public 本身：擁有者 sysadm、群組 sftpusers、**setgid + sticky（3770）** + ACL u:anonymous:r-x
B> 檢查：**getfacl** 看 ACL、**ls -l** 中權限後面有 **+** 代表有 ACL；以 anonymous 實際 get 測試
X> chown sysadm:sftpusers /mnt/hw2/sftp/public
X> chmod 3770 /mnt/hw2/sftp/public
X> setfacl -m u:anonymous:rx,u:sysadm:rwx /mnt/hw2/sftp/public
X> setfacl -d -m u::rwx,g::rwx,o::---,u:anonymous:rx,u:sysadm:rwx /mnt/hw2/sftp/public
X> getfacl /mnt/hw2/sftp/public
?mc sftp-u1 上傳的檔案權限是 -rw-rw----（群組 sftpusers），沒有 ACL。anonymous 能 get 它嗎？
+ 不能，anonymous 不是擁有者也不在 sftpusers，屬於 other，而 other 沒有權限
- 能，anonymous 是唯讀帳號，系統會讓它讀取 SFTP 根目錄底下所有的檔案
- 能，SFTP 的 chroot 會讓 anonymous 以 sftpusers 群組的身分存取 public 底下的檔案
- 只有在 public 設了 sticky bit 時，anonymous 才能讀取別人上傳的檔案
E> 目錄的權限只決定能不能列出與進入，讀檔要看檔案本身的權限。
?mc 為什麼用「預設 ACL 給 anonymous r」可以同時滿足「上傳檔 other 無權限」與「anonymous 可讀」？
+ anonymous 透過具名使用者 ACL 取得讀取權，不依賴 other 位元，other 仍可以是 ---
- ACL 會把 anonymous 改成上傳檔案的擁有者，所以它能讀取
- 設定預設 ACL 後，系統會在 anonymous 讀取時暫時把 other 改成 r--，讀完再改回 ---
- 預設 ACL 會讓 umask 失效，other 變成 rwx，所以 anonymous 讀得到
E> ls -l 看到的 other 欄位仍是 ---，滿足評分條件。
?cmd 讓之後在 public 中新建的檔案，自動給使用者 anonymous 讀取（與目錄進入）權限：
= setfacl -d -m u:anonymous:rx public
= setfacl -d -m u:anonymous:r-x public
= setfacl -m d:u:anonymous:rx public
= setfacl -m d:u:anonymous:r-x public
= setfacl --default -m u:anonymous:rx public
E> -d（--default）設定預設 ACL；d:u:… 是等價寫法。
?tf ls -l 顯示 -rw-rw----+，最後的 + 表示這個檔案有額外的 ACL。
=T
E> 用 getfacl 查看完整內容。

@CARD hw2.p_privdesign | 2-2 實戰：private 與 hidden 的「能進不能看」
A> private 像一條「沒有門牌的走廊」：大家能走進去（x），但看不到裡面有哪些房間（沒有 r 就不能 ls）；只要你知道房間名字（hidden），就能直接走到；房間裡的寶藏（treasure）有開放讀取，所以拿得到。
B> 目錄的 **r**：列出內容（ls）；**x**：進入與存取已知名稱的檔案（cd、get 已知路徑）；**w + x**：新增、刪除、改名
B> private、hidden：擁有者 **sysadm**，模式 **711**（group 與 other 只有 --x）→ 會員與訪客能 cd、不能 ls、不能寫
B> **treasure**：**644**（other 可讀）→ 知道路徑就能 get
B> sysadm 是擁有者 → private 底下 get/put/mkdir/rm/rmdir 都可以
B> sftp_watchd 的 **private/.violated/**：建議 root 擁有、700，避免使用者讀取違規檔
X> install -d -o sysadm -g sysadm -m 711 /mnt/hw2/sftp/private /mnt/hw2/sftp/private/hidden
X> install -o sysadm -g sysadm -m 644 /dev/null /mnt/hw2/sftp/private/hidden/treasure
X> install -d -o root -g root -m 700 /mnt/hw2/sftp/private/.violated
?mt 配對目錄權限位元的效果：
> r :: 可以列出目錄內容（ls）
> x :: 可以進入目錄、存取已知名稱的項目
> w（搭配 x） :: 可以新增、刪除、改名目錄中的項目
E> 目錄的 x 也叫 search 權限：沿路徑往下走需要每一層都有 x。
?mc private 目錄權限為 drwx--x--x（711），擁有者 sysadm。sftp-u1 執行 ls private 與 get private/hidden/treasure（treasure 為 644、hidden 也是 711）會？

- 兩者都失敗
- ls 成功；get 失敗
E> 沒有 r 不能列目錄；有 x 可以沿已知路徑走到 treasure，而 treasure 對 other 可讀。
?fill 讓 other「能進入但不能列出」的目錄權限（擁有者 rwx）是 chmod ＿＿ private

@CARD hw2.p_watchimpl | 2-3 實戰：sftp_watchd 實作細節
A> sftp_watchd 是一位「收件室管理員」：盯著 SFTP 目錄，每當有人「寫完」一個檔案（close_write），就檢查前 4 個 byte 是不是 ELF 的魔術數字、算 MD5 比對黑名單，違規就搬進 .violated 並照固定格式記錄。它本身不能 fork 到背景，交給 systemd 管。
B> 監看：**inotifywait -m -r -e close_write,moved_to --format '%w%f' --exclude '/\.violated/' /mnt/hw2/sftp**（需 apt install **inotify-tools**）
B> **close_write**：檔案寫完才觸發（避免檢查到傳到一半的檔案）；**moved_to**：檔案被改名移入；**-r** 新建子目錄也會自動監看
B> ELF 判斷：前 4 bytes 為 **7f 45 4c 46**（\x7fELF）：**head -c 4 "$f" | od -An -tx1**
B> MD5：**md5sum "$f" | cut -d' ' -f1** 與黑名單比對；上傳者：**stat -c %U "$f"**
B> 搬移：mv 到 **private/.violated/**（處理同名衝突）；log 印到 **stdout** → journal；訊息**一字不差**
B> 規則：**不能呼叫其他自己寫的程式**（系統工具如 inotifywait、md5sum 可以）；放在 PATH（/usr/local/bin）、judge 讀得到
X> inotifywait -m -r -q -e close_write,moved_to --format '%w%f' --exclude '/\.violated/' "$SFTP_ROOT" |
X> while IFS= read -r f; do
X>   [ -f "$f" ] || continue
X>   user=$(stat -c %U "$f")
X>   if [ "$(head -c 4 "$f" | od -An -tx1 | tr -d ' \n')" = 7f454c46 ]; then
X>     echo "File $f uploaded by user $user is an ELF file. Moving to violated directory"
X>     mv -- "$f" "$SFTP_ROOT/private/.violated/"
X>   fi
X> done
?mc 為什麼用 close_write 而不是 create 事件來觸發檢查？
+ create 時內容還沒傳完
- create 事件只對目錄有效
- close_write 比較省 CPU
- inotify 沒有 create 事件
E> create 在檔案剛建立（內容還沒傳完）就觸發；close_write 在寫入完成、關閉檔案時才觸發。檔案還沒傳完就計算 MD5，結果一定不對。
?fill ELF 檔案開頭 4 個 byte 的十六進位是 7f 45 4c ＿＿
= 46
E> 也就是 0x7F 'E' 'L' 'F'。
?mc 把違規檔搬進 private/.violated/ 後，watcher 又對它觸發 moved_to 事件而重複處理。最好的修法？
+ 監看時用 --exclude 排除 .violated 目錄（或處理前先檢查路徑）
- 改用 cp 而不要 mv，這樣就不會產生 moved_to 事件
- 把 .violated 放到 public 目錄裡，讓 watcher 把它當成一般檔案
- 每次處理完一個檔案就重啟服務，清除 inotify 的事件佇列
E> 搬移本身就是一個 moved_to 事件。
?cmd 取得檔案 /mnt/hw2/sftp/public/a.bin 擁有者的使用者名稱：
= stat -c %U /mnt/hw2/sftp/public/a.bin
= stat --format=%U /mnt/hw2/sftp/public/a.bin
= stat -c '%U' /mnt/hw2/sftp/public/a.bin
E> 上傳的檔案由該 SFTP 使用者建立，擁有者就是上傳者。
