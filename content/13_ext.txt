@CARD ext1.imgsize | 縮小 Docker image
A> Image 是一層層疊起來的千層蛋糕，每一層一旦烤好就永遠在裡面，在後面一層「刪掉」前面的東西，蛋糕不會變輕。所以要：選小的底（slim/alpine）、同一層裡裝完就清垃圾、用 multi-stage 只把成品搬進新蛋糕、用 .dockerignore 不要把雜物帶進廚房。
B> 用較小的 **base image**：*-slim、alpine、distroless、scratch
B> **Multi-stage build**：編譯在 builder stage，最後 stage 只 COPY --from 成品
B> **合併 RUN 並在同一層清理**：apt-get install --no-install-recommends … && rm -rf /var/lib/apt/lists/*（在不同層刪除不會變小）
B> **.dockerignore** 排除 .git、node_modules、測試資料等不必要的 build context
B> 只安裝 runtime 需要的套件；移除 build 工具與快取（pip --no-cache-dir）
?sa 如何在維持相同功能狀況下減少 docker build 出來的 Docker image 大小？列出至少三種方式。
S> 2025 期末 Q5
R> ① 使用較小的 base image，例如 debian:trixie-slim、alpine、distroless 取代完整版 image。
R> ② 使用 multi-stage build：在前面的 stage 安裝編譯工具並 build，最後的 stage 只用乾淨的 runtime image 並 COPY --from=builder 需要的執行檔 / 產物，編譯器與原始碼不會留在最終 image。
R> ③ 減少 layer 並在同一個 RUN 中清理：把多個 RUN 合併，安裝後立即刪除套件快取（apt-get install --no-install-recommends … && rm -rf /var/lib/apt/lists/*、pip --no-cache-dir），因為在後面的 layer 刪除檔案不會讓前面 layer 變小。
R> ④ 使用 .dockerignore 排除不需要的檔案（.git、測試資料、node_modules），避免被 COPY 進 image。
R> ⑤ 只安裝必要套件、移除 build-time 依賴。
P> 較小的 base image
P> multi-stage build
P> 同一層 RUN 內清除快取 / 合併 layer
P> .dockerignore 或只裝必要套件

@CARD ext1.multistage | Multi-stage build 的使用時機
A> Multi-stage 像「在工廠做好家具，只把成品搬進新家」：工廠裡的鋸子、刨木屑（編譯器、原始碼、dev 套件）都不會跟進家門。所以只要「建置時需要、執行時不需要」的東西很多，就適合用。
B> 適用：**build-time 依賴在 runtime 不需要**時
B> 例：編譯語言（C/C++、Go、Rust、Java）先編譯，最後只拷貝 binary / jar；前端專案 npm build 後只把靜態檔放進 nginx image
B> 好處：image 更小、攻擊面更小、不洩漏原始碼 / 建置憑證
X> FROM golang:1.23 AS builder
X> WORKDIR /src
X> COPY . .
X> RUN go build -o app
X> FROM debian:trixie-slim
X> COPY --from=builder /src/app /usr/local/bin/app
X> CMD ["app"]
?sa 在何種情況下可以在 docker build 時使用 multi-stage building 技巧？
S> 2025 期末 Q6
R> 當建置（build）過程需要的工具或依賴，在執行（runtime）時並不需要的情況。例如需要編譯器、SDK、dev headers 來編譯程式（C/Go/Rust/Java），或前端需要 Node.js 與 npm 套件來 build 靜態檔，但最後執行只需要編譯出的 binary 或靜態檔。這時可在第一個 stage 安裝工具並 build，最後的 stage 以精簡的 base image 並用 COPY --from=<stage> 只複製產物，最終 image 不含 build 工具與原始碼，更小也更安全。
P> build-time 需要但 runtime 不需要的依賴
P> 舉例（編譯型語言 / 前端 build）並說明只複製產物

@CARD ext1.secrets | Docker：環境變數 vs secrets
A> 環境變數像「把密碼寫在名牌上」：方便，但任何能看你名牌的人（docker inspect、/proc/<pid>/environ、子程序、log）都看得到。Secret 像「放在只有你能開的保險箱」：以檔案形式掛在 /run/secrets/ 下的 tmpfs，只有被授權的服務拿得到。
B> **環境變數**：-e / --env-file / compose environment:；程式讀 $VAR；簡單通用
B> 風險：**docker inspect** 看得到、**/proc/<pid>/environ**、child process 繼承、可能被印進 log / crash dump；若寫在 Dockerfile **ENV** 會留在 image layer
B> **Secrets**（Swarm / Compose）：以**檔案**掛在 **/run/secrets/<name>**（記憶體 tmpfs），Swarm 中加密儲存與傳輸，只給被授權的 service；不出現在 inspect / 環境中
B> 限制：程式要支援從檔案讀（常見 *_FILE 慣例，如 POSTGRES_PASSWORD_FILE）；需要 Swarm / Compose；Swarm secret 不可變（輪替要建新的）、大小有上限（約 500KB）
?sa 在 Docker 容器中設定機敏資料（例如資料庫密碼）時，可以使用環境變數或 secrets，請從使用方式、安全性以及限制三個方面分析兩者的不同。
S> 2025 期末 Q23
R> 使用方式：環境變數透過 docker run -e、--env-file 或 compose 的 environment: 設定，程式直接讀環境變數；secrets 透過 Docker Swarm 或 Compose 的 secrets: 定義並指派給 service，在容器中以檔案形式出現在 /run/secrets/<name>，程式要去讀檔（很多官方 image 支援 XXX_FILE 變數指定檔案路徑）。
R> 安全性：環境變數是明文存在 container 設定中，docker inspect、/proc/<pid>/environ 都看得到，會被所有子程序繼承，也容易被意外印到 log 或錯誤報告；寫在 Dockerfile ENV 甚至會留在 image layer。Secrets 不會出現在 inspect 與環境變數中，以 tmpfs（記憶體）掛載、不落地，Swarm 中在 Raft log 加密、傳輸加密，只有被授權的 service 能存取。
R> 限制：環境變數幾乎所有程式都支援、最簡單，但不適合高敏感資料；secrets 需要 Swarm 或 Compose 支援（單純 docker run 沒有）、程式必須支援從檔案讀取、Swarm secret 建立後不可修改（要輪替需建新 secret 並更新 service）、大小有上限。
P> 使用方式：env 透過 -e/environment；secret 以檔案 /run/secrets 提供
P> 安全性：env 可被 inspect / proc / log 洩漏；secret 不在環境中、tmpfs、加密、限定 service
P> 限制：secret 需 Swarm/Compose、程式要讀檔、不可變等
?fill Docker secret 在容器內預設以檔案出現在 /run/＿＿/<name>
= secrets
E> /run/secrets/。

@CARD ext1.compose | Docker Compose 網路與服務名稱解析
A> Compose 幫你的專案開一個「私人社區網路」（user-defined bridge），社區裡有一位內建的「管理員」（Docker embedded DNS，127.0.0.11）。你喊「db」，管理員就告訴你 db 那個 container 在社區裡的 IP。
B> Compose 預設為專案建立一個 **user-defined bridge network**（<project>_default）
B> user-defined network 有 **Docker 內建 DNS server（127.0.0.11）**，把 **service 名稱**（以及 container 名稱、alias）解析成 container 的 IP
B> 拿到的是該 container 在**這個 Compose 網路上的內部 IP**（不是 host IP、不是 published port）；scale 多個副本時解析到多個 IP
B> 預設的 docker0 bridge（沒用 Compose 的 docker run）**沒有**這種名稱解析
?sa 在 Docker Compose 預設的 bridge network 中，不同的 service 之間為何可以使用 hostname 連線？使用 hostname 連線時他們會拿到哪個 IP？
S> 2025 期末 Q26
R> Compose 會為專案建立一個 user-defined bridge network，並把每個 service 的 container 接上去、以 service 名稱註冊為網路別名。Docker 在 user-defined network 上提供內建 DNS server（容器內的 127.0.0.11），容器查詢其他 service 的名稱時，由它解析，所以可以直接用 service 名稱當 hostname 連線。
R> 解析得到的是目標 container 在這個 Compose 網路上的內部（私有）IP，例如 172.18.0.x，而不是 host 的 IP 或對外 publish 的 port；若該 service 有多個副本則會回傳多個 container IP。
P> Compose 建立 user-defined bridge，Docker embedded DNS 解析 service 名稱
P> 拿到目標 container 在該網路的內部 IP
?tf 在 Compose 中，web 服務連 db:5432 時，需要先把 db 的 5432 用 -p publish 到 host。
=F
E> 同一個 Compose 網路內直接用內部 IP 與 container port 溝通，不需 publish。

@CARD ext1.nfsiscsi | NFS vs iSCSI
A> NFS 是「共享資料夾」：伺服器管檔案系統，大家用網路來拿「檔案」，可以多人同時存取；iSCSI 是「用網路線接一顆硬碟」：伺服器只提供「一整塊空白的區塊裝置」，client 自己格式化、自己管檔案系統，通常一次只給一台用（否則檔案系統會壞）。
B> **NFS**：**檔案層級（file-level）**共享；檔案系統在 server 端；多個 client 可**同時掛載**存取同一批檔案；權限 / 鎖由 server 處理
B> **iSCSI**：**區塊層級（block-level）**，把 SCSI 指令封裝在 TCP/IP 中；client（initiator）看到的是一顆 **raw 磁碟**（target 的 LUN），自己 mkfs、自己管檔案系統；一般**不可多台同時掛載**一般檔案系統（除非用 cluster FS）
B> 適用：NFS → 多台主機共享家目錄、共用資料夾、web 叢集共用靜態檔；iSCSI → VM 磁碟映像、資料庫儲存、需要區塊裝置 / 開機磁碟、較好的效能
?sa 請比較並說明 2 點 NFS 與 iSCSI 的差異，並分別舉例說明什麼情況適合使用它們。
S> 2025 期末 Q9
R> 差異 1（層級）：NFS 是檔案層級的網路檔案系統，server 管理檔案系統，client 透過網路存取「檔案」；iSCSI 是區塊層級協定，把 SCSI 指令封裝在 TCP/IP 上，client 看到的是一顆原始磁碟（block device），由 client 自己建立與管理檔案系統。
R> 差異 2（共享性）：NFS 天生支援多個 client 同時掛載並存取同一批檔案，鎖與權限由 server 協調；iSCSI 的 LUN 通常只給一台主機使用，多台同時掛載一般檔案系統（ext4 等）會造成資料損毀，除非使用 cluster filesystem。
R> （其他差異：iSCSI 效能較接近本機磁碟、可當開機碟；NFS 設定簡單、可直接在 server 端備份檔案。）
R> 適用情境：NFS 適合多台機器共享家目錄、共用資料夾、web 叢集共享靜態檔案；iSCSI 適合需要專屬區塊裝置的情況，例如 VM 的虛擬磁碟、資料庫的儲存空間、無碟主機的開機磁碟。
P> 檔案層級 vs 區塊層級
P> 多 client 共享 vs 通常單一主機獨占（client 自己管 FS）
P> NFS 適用情境舉例
P> iSCSI 適用情境舉例
?mt 配對 NFS / iSCSI：
> client 看到一顆 raw 磁碟，自己 mkfs :: iSCSI
> 多台主機同時掛載共享檔案 :: NFS
> 檔案系統由 server 管理 :: NFS
> 適合當 VM 的虛擬磁碟 :: iSCSI
E> file-level vs block-level。

@CARD ext1.acme | ACME http-01 challenge
A> 證明「這個網址是我的」：CA 給你一個暗號（token），你把寫著暗號 + 你帳號指紋的紙條貼在自己網站的指定位置（/.well-known/acme-challenge/<token>），CA 從外面連過來看，看到了就相信網站是你在控制。
B> ACME client（如 Certbot）向 CA（Let's Encrypt）下單，CA 給 **token**
B> client 在網站放檔案：**http://<domain>/.well-known/acme-challenge/<token>**，內容為 **key authorization**（token + 帳號公鑰 thumbprint）
B> CA 透過 **HTTP port 80** 對該網域發出請求；內容正確 → 證明控制該網域的 web server → 簽發憑證
B> http-01 **不支援 wildcard（*.example.com）**：它只能驗證「某一個特定 hostname」能被連到，無法證明你控制整個網域底下所有子網域；Let's Encrypt 規定 wildcard 必須用 **dns-01**（在 _acme-challenge.<domain> 放 TXT record，證明控制 DNS zone）
?sa 請簡單說明 ACME http-01 challenge 的核心運作原理。ACME client（例如 Certbot）該如何證明它擁有某個特定網域的控制權？
S> 2025 期末 Q24
R> ACME client 向 CA 申請某網域的憑證時，CA 會發出一個 http-01 challenge，內含隨機 token。Client 要在該網域的 web server 上，把內容為 key authorization（token 加上 ACME 帳號公鑰的 thumbprint）的檔案放在 http://<domain>/.well-known/acme-challenge/<token>，然後通知 CA 可以驗證。
R> CA 從多個網路位置透過 HTTP（port 80）去存取這個 URL，若取得的內容與預期相符，就證明申請者能控制該網域所指向的 web server，因此擁有該網域的控制權，CA 便簽發憑證。
P> CA 發 token；client 放檔案到 /.well-known/acme-challenge/<token>
P> 內容為 key authorization（token + 帳號金鑰 thumbprint）
P> CA 經 HTTP 80 存取驗證，成功即證明控制權
?sa 為什麼 ACME http-01 challenge 沒辦法支援萬用字元憑證（wildcard certificate）？
S> 2025 期末 Q25
R> http-01 是由 CA 對「一個具體的 hostname」發出 HTTP 請求來驗證，只能證明你控制該 hostname 所指向的那台 web server。Wildcard 憑證 *.example.com 涵蓋的是無限多個（甚至尚未存在的）子網域，CA 無法對 * 發出 HTTP 請求，也無法逐一驗證所有子網域；能控制某台 web server 並不代表能控制整個網域。
R> 要證明擁有整個網域的控制權，必須證明能修改該網域的 DNS，因此 ACME（Let's Encrypt）規定 wildcard 憑證只能使用 dns-01 challenge（在 _acme-challenge.example.com 放指定的 TXT record）。
P> http-01 只能驗證特定 hostname 的 web server
P> wildcard 涵蓋無限子網域，無法用 HTTP 驗證，需證明控制整個 DNS zone
P> 必須改用 dns-01
?mc 想申請 *.example.com 的 Let's Encrypt 憑證，必須使用哪種 challenge？
+ dns-01
- http-01
- tls-alpn-01
- 任何一種都可以
E> wildcard 需要 dns-01。

@CARD ext1.oauth | OAuth2 client credentials 與 OIDC discovery
A> Client credentials flow 是「機器對機器的員工證」：沒有使用者在場，服務直接拿自己的帳號密碼（client_id / client_secret）去櫃台（token endpoint）換一張通行證（access token）。OIDC 的 /.well-known/openid-configuration 是「這家認證中心的服務目錄」，client 讀它就知道該去哪個窗口辦事。
B> **Client credentials flow**：**machine-to-machine**，沒有使用者參與；client 以 **client_id + client_secret**（或 private key JWT）直接向 **token endpoint** 送 grant_type=client_credentials，取得 **access token** 去呼叫 API；通常沒有 refresh token
B> **OIDC discovery**：GET **/.well-known/openid-configuration** 回傳 JSON metadata，讓 client 自動設定
B> 可取得：**issuer**、**authorization_endpoint**、**token_endpoint**、**userinfo_endpoint**、**jwks_uri**（驗 ID token 簽章的公鑰）、scopes_supported、response_types_supported、grant_types_supported、id_token_signing_alg_values_supported、end_session_endpoint
?sa 請說明 OpenID Provider 的 /.well-known/openid-configuration 有何作用？並列出三種可以從該端點獲取的資訊。
S> 2025 期末 Q27
R> 這是 OpenID Connect 的 discovery 端點，回傳一份 JSON 格式的 provider metadata，讓 client（Relying Party）不用手動寫死各種 URL 與設定，只要知道 issuer 就能自動探索並設定與該 OpenID Provider 互動所需的資訊。
R> 可取得的資訊例如：issuer（發行者識別）、authorization_endpoint（授權端點）、token_endpoint（換 token 的端點）、userinfo_endpoint（取得使用者資訊）、jwks_uri（驗證 ID token 簽章用的公鑰集合）、scopes_supported、response_types_supported、grant_types_supported、id_token_signing_alg_values_supported。
P> 作用：discovery，提供 metadata 讓 client 自動設定
P> 列出三項正確資訊（如 authorization / token endpoint、jwks_uri、issuer）
?sa 請簡單說明 OAuth2 中的 client credentials flow。
S> 2025 期末 Q28
R> Client credentials flow 用於機器對機器（服務對服務）的授權，沒有終端使用者參與。Client 事先在授權伺服器註冊取得 client_id 與 client_secret；需要存取 API 時，直接向授權伺服器的 token endpoint 發送請求（grant_type=client_credentials，附上 client 認證與要求的 scope），授權伺服器驗證 client 身分後回傳 access token，client 再帶著這個 access token 去呼叫 resource server 的 API。權限代表的是 client 本身而非某位使用者，通常不發 refresh token。
P> machine-to-machine，沒有使用者
P> client_id / secret 直接到 token endpoint 換 access token
P> 用 access token 存取 API
?mt 配對 OIDC metadata 欄位：
> token_endpoint :: 用授權碼或 client 憑證換取 token 的位置
> jwks_uri :: 驗證簽章用的公鑰集合
> authorization_endpoint :: 導向使用者登入 / 授權的位置
> issuer :: Provider 的識別字串
E> 這些都在 /.well-known/openid-configuration 中。

@CARD ext1.tls | TLS 與 CA
A> TLS 握手像「先用掛號信（非對稱加密，慢但不怕被偷看）交換一把保險箱鑰匙，之後就用這把鑰匙（對稱加密，快）傳所有東西」。向 CA 申請憑證時，你交出的是公鑰（裝在 CSR 裡）與身分證明，私鑰永遠只留在自己手上。
B> TLS **建立連線（handshake）** 用 **非對稱加密** / 金鑰交換（RSA、(EC)DHE）與憑證驗證身分 → 協商出 **session key**
B> 之後的資料傳輸用**對稱加密**（AES、ChaCha20），因為快
B> 向 CA 申請憑證要提供：**公鑰**（包在 **CSR 憑證請求檔**中）、**身分證明文件**（OV/EV）；**絕不提供私鑰**
?mc TLS/SSL「建立連線時（handshake）」使用的是哪一種加密方式？
+ 非對稱式加密
- 對稱式加密
- 未加密
- 以上皆非
S> 2023 期末 Q2
E> 握手階段用非對稱（公鑰）機制，之後的資料傳輸才用協商出的對稱金鑰。
?mc 下列哪一個「不是」向 CA 申請憑證所需提供的資訊？
+ 私鑰
- 公鑰
- 憑證請求檔（CSR）

@CARD ext1.http | HTTP/2 與 HTTP/3
A> HTTP/1.1 像「一條單線道，前面的車卡住後面全部等」；HTTP/2 把一條 TCP 連線切成很多「虛擬車道」（multiplexing streams），還把標頭壓縮；但底下的 TCP 掉一個封包，所有車道還是一起等。HTTP/3 改走 QUIC（UDP 上），每條車道獨立，掉包只影響自己那條，而且握手更快。
B> **HTTP/2**：**Multiplexing**（單一 TCP 連線上多個 stream 並行，解決 HTTP 層 head-of-line blocking）、**HPACK header compression**、**binary framing**、server push、stream priority
B> **HTTP/3**：跑在 **QUIC（UDP）** 上 → 消除 **TCP 層的 head-of-line blocking**（stream 獨立）、**TLS 1.3 整合**，握手 1-RTT / **0-RTT**、**connection migration**（以 connection ID 識別，換網路不斷線）

@CARD ext2.pf | 防火牆：nftables 與 drop vs reject

X>   chain input {
X>     type filter hook input priority 0; policy drop;
X>     ct state established,related accept
X>     iif lo accept
X>     tcp dport 22 accept
X>     udp dport 53 reject
X>   }
X> }

@CARD ext2.man | man pages：章節與語法

@CARD ext2.linuxbsd | systemd vs 傳統 SysV init（Debian 的前後對照）
A> SysV init 像「照號碼排隊、一個一個叫號」：/etc/rcN.d 裡 S20、S30 的連結決定先後，每個服務是一支 shell 腳本，自己記 PID 檔。systemd 像「看相依關係同時開好幾個窗口」：unit 檔宣告需要誰、排在誰之後，能平行啟動，並用 cgroup 盯住每個服務生出來的所有 process。
B> **服務定義**：SysV 是 **/etc/init.d/** 的 shell 腳本（start / stop 自己寫）；systemd 是宣告式 **unit 檔**（ExecStart=、Restart=）
B> **開機順序**：SysV 依 **rcN.d 的 S/K 編號**依序執行；systemd 依 **Requires= / Wants= + After=** 建相依關係，可**平行**啟動
B> **執行等級**：SysV 是 **runlevel 0–6**；systemd 是 **target**（1 ≈ rescue.target、3 ≈ multi-user.target、5 ≈ graphical.target）
B> **開機啟用**：SysV 用 update-rc.d 建 S/K 連結；systemd 用 **systemctl enable**（建 .wants/ symlink）
B> **追蹤 process**：SysV 靠 **PID 檔**（/var/run/*.pid），fork 出去的子行程可能漏掉；systemd 用 **cgroup** 追蹤所有後代
B> **log**：SysV 靠 syslog 寫文字檔；systemd 有 **journald**，journalctl -u 依服務查詢
B> **自動重啟、資源限制**：SysV 要自己寫；systemd 有 **Restart=**、**MemoryMax=**、**CPUQuota=**
B> 對照：FreeBSD 也是腳本式（/etc/rc.d 加上 /etc/rc.conf 的 xxx_enable="YES"、service、sysrc）
?sa 試舉出三個 Debian 使用的 systemd 與傳統 SysV init 不同之處（需明確指出 systemd 如何、SysV 如何，「名字 / 開發者不同」這類答案不計分）。
S> 2023 期中 Q13（改編為 Debian 版）
R> ① 服務定義：SysV 的每個服務是 /etc/init.d/ 下的一支 shell 腳本，start / stop 的邏輯自己寫；systemd 用宣告式的 unit 檔（如 ExecStart=、Restart=），由 systemctl 統一管理。
R> ② 啟動順序：SysV 依 /etc/rcN.d 裡 S/K 連結的編號，一個接一個執行；systemd 由 Requires= / Wants= 與 After= 建立相依關係，沒有相依的服務可以平行啟動，開機較快。
R> ③ 執行等級：SysV 用數字 runlevel（0–6，例如 3 是多使用者文字模式）；systemd 用 target（multi-user.target、graphical.target、rescue.target），一個 target 是一組 unit 的集合，可以同時有多個 active。
R> 其他：process 追蹤（PID 檔 vs cgroup）、log（syslog 文字檔 vs journald）、開機啟用（update-rc.d 建連結 vs systemctl enable 建 .wants symlink）、自動重啟與資源限制（自己實作 vs Restart=、MemoryMax=）。
P> 三個具體差異，每個都明確說明 systemd 與 SysV 各自的做法
?mt 配對傳統 SysV 做法與 Debian（systemd）的對應：
> /etc/init.d 腳本 + rcN.d 連結 :: unit 檔 + systemctl enable
> runlevel 3 :: multi-user.target
> /var/run/*.pid 追蹤服務 :: cgroup 追蹤所有後代 process
> 只寫 syslog 文字檔 :: journald + journalctl -u
E> 寫差異題時，每一點都要講清楚兩邊各怎麼做。
