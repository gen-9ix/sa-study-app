@CARD hw3.pki | 自建 PKI：Root CA 與 Intermediate CA
A> 自己開一間「發證中心」：Root CA 是總部的鋼印，平常鎖在保險箱；Intermediate CA 是分部的印章，日常發證都用它。分部印章被限制「只能發一般證件，不能再開分部」（pathlen:0）。客戶只要信任總部，就能沿著鏈條驗證所有證件。
B> **Root CA**：自簽；Subject C=TW, O=National Yang Ming Chiao Tung University, CN=SA-{STU_ID} Root CA；**/home/judge/hw3/ca/root.crt**
B> **Intermediate CA**：由 root 簽發；**不能再簽其他 CA 憑證** → **basicConstraints = critical, CA:TRUE, pathlen:0**；keyUsage keyCertSign, cRLSign
B> **VM 要信任你的 root CA**；intermediate 簽發 Part 1 所有主機的 **TLS 憑證**與所有 **client 憑證**
B> 伺服器憑證：主機名放在 **SAN（subjectAltName）**（現代用戶端不看 CN）、EKU **serverAuth**；client 憑證：EKU **clientAuth**
B> 伺服器要送 **leaf + intermediate**（fullchain），用戶端用 root 驗證整條鏈
X> openssl req -x509 -new -key root.key -days 3650 -subj "/C=TW/O=National Yang Ming Chiao Tung University/CN=SA-19 Root CA" -out root.crt
X> # intermediate 的 extension
X> basicConstraints = critical, CA:TRUE, pathlen:0
X> keyUsage = critical, keyCertSign, cRLSign
X> openssl verify -CAfile root.crt -untrusted intermediate.crt server.crt
?mc 要讓 intermediate CA「可以簽發一般憑證，但不能再簽其他 CA」，應設定？
+ basicConstraints = CA:TRUE, pathlen:0
- keyUsage = keyCertSign, digitalSignature
- keyUsage = digitalSignature
- extendedKeyUsage = serverAuth
E> pathlen:0 表示它底下不能再有 CA；CA:FALSE 則連一般憑證都不能簽（它就不是 CA 了）。
?mc 現代瀏覽器檢查憑證是否屬於 git.19.cs.nycu 時，看的是？
+ SAN（subjectAltName）中的 DNS 名稱
- Subject 的 O（organization）
- 憑證的序號
- Issuer 的 CN
E> 只看 SAN；沒有 SAN 的憑證會被拒絕。
?cmd 用 root.crt 當信任根、intermediate.crt 當中繼，驗證 server.crt：
= openssl verify -CAfile root.crt -untrusted intermediate.crt server.crt
E> -untrusted 提供中繼憑證，但不把它當成信任根。
?mt 配對憑證 extension：
> basicConstraints CA:TRUE, pathlen:0 :: 只能簽發終端憑證的中繼 CA
> subjectAltName DNS:pg.19.cs.nycu :: 憑證適用的主機名稱
> extendedKeyUsage serverAuth :: 可用於 TLS 伺服器
> extendedKeyUsage clientAuth :: 可用於 TLS 用戶端認證（mTLS）
E> 伺服器憑證放 serverAuth 與 SAN；mTLS 的 client 憑證放 clientAuth。
?sa 請說明為什麼實務上會用「Root CA + Intermediate CA」兩層架構，而不是直接用 Root CA 簽所有伺服器憑證？並說明用戶端如何驗證一張由 intermediate 簽發的伺服器憑證。
R> 原因：Root CA 的私鑰是整個信任體系的根，一旦外洩所有憑證都失去意義，而且 root 已預先安裝在各用戶端的信任清單中，更換成本極高。因此 root 私鑰應離線保存、極少使用，只用來簽發 intermediate；日常簽發由 intermediate 負責。intermediate 若外洩，可以由 root 撤銷（CRL/OCSP）並重發新的 intermediate，不必更動所有用戶端的信任根；也可以為不同用途分出不同的 intermediate 並以 pathlen、name constraints 限制權限。
R> 驗證：伺服器在 TLS handshake 送出 leaf 憑證與 intermediate 憑證。用戶端用 intermediate 的公鑰驗證 leaf 的簽章、用自己信任清單中的 root 公鑰驗證 intermediate 的簽章，建立 leaf → intermediate → root 的鏈；同時檢查每張憑證的有效期限、basicConstraints（中間節點必須是 CA 且符合 pathlen）、keyUsage/EKU（leaf 需 serverAuth）、leaf 的 SAN 是否符合連線的主機名，以及撤銷狀態。
P> root 私鑰離線保存、降低外洩風險
P> intermediate 外洩可撤銷並重發，不必更換用戶端信任根
P> 伺服器送出 leaf + intermediate，用戶端逐層驗簽章直到信任的 root
P> 檢查有效期、CA 限制、EKU、SAN 主機名、撤銷

@CARD hw3.weakca | 有缺陷的 Intermediate CA：私鑰可被算出
A> RSA 的安全性靠「兩個超大質數相乘很容易，反過來分解很難」。如果私鑰是用很小的數字產生的，壞人就能把公鑰的 n 分解掉、算出私鑰，等於偷到 CA 的印章，可以替任何網站發「合法」的假證件，瀏覽器也會相信。
B> 背景：2026 年 10 月 Mozilla 發現 8 張 **eMudhra** intermediate CA 憑證的私鑰來自**非常小的數字** → 任何人都能算出私鑰
B> 作業中 TA root CA 也替每位學生簽了一張**同樣有缺陷的 intermediate CA**，並用它簽發 https://{STU_ID}.vuln.ta.cs.nycu
B> 要求：在 /etc/hosts 把 {STU_ID}.vuln.ta.cs.nycu 指向自己，用**算出私鑰的缺陷 CA** 簽一張 **SAN 只有該主機名**的憑證，能通過 **TA root CA** 驗證，回應原站內容並加上 header **X-Intercepted-By: {STU_ID}**
B> 教訓：CA 私鑰外洩 = 可以冒充任何網站；所以需要**撤銷（CRL / OCSP）**、**Certificate Transparency**，以及正確的金鑰產生
?mc 為什麼拿到一張 intermediate CA 的私鑰，就能冒充網站且瀏覽器不會警告？
+ 用它簽出的憑證可以串到瀏覽器信任的 root，整條鏈驗證都會通過
- 因為瀏覽器不檢查 intermediate
- 因為 intermediate 的私鑰也能解密所有 TLS 流量
- 因為這種憑證不需要 SAN
E> 信任是沿著鏈傳遞的，所以 CA 私鑰外洩後必須撤銷那張 intermediate。
?mc RSA 私鑰若由「很小的數字」產生，為什麼不安全？
+ 公鑰的模數 n 可以被輕易分解成兩個質數，進而算出私鑰
- 小數字產生的簽章長度太短，用戶端無法驗證
- 公鑰的長度會變成 0，憑證被視為空白而直接被信任
- 小數字產生的憑證無法放入 SAN 欄位
E> RSA 的安全性建立在大整數分解的困難度上。
?tf CA 私鑰外洩後，最主要的補救方式是把該 CA 憑證撤銷（例如列入上層 CA 的 CRL）。
=T
E> 撤銷後，檢查 CRL 的用戶端就會拒絕它簽出的所有憑證（這正是 tls_revoked 的情境）。

@CARD hw3.nginxtls | NGINX：HTTPS、301、HSTS、隱藏 header
A> NGINX 是大門口的警衛：所有 HTTP 訪客都被請到 HTTPS 門口（301 永久轉址）；HSTS 是「告訴瀏覽器以後一年內直接走 HTTPS，別再走 HTTP」；不要告訴外人裡面用的是什麼軟體、什麼版本（拿掉 Server、X-Powered-By、Via）。
B> Part 1 所有主機（pg 除外）：**HTTPS**（你的 CA 簽的憑證）、**HTTP → HTTPS 用 301**、**HSTS max-age ≥ 31536000**
B> 依主機轉發到 port 表中的服務（**reverse proxy**）
B> 回應**不能有 Server、X-Powered-By、Via** header
B> **server_tokens off** 只會拿掉版本號，Server: nginx 還在；完全移除要用 **headers-more** 模組（more_clear_headers Server）
B> 後端送出的 header 用 **proxy_hide_header X-Powered-By;** 隱藏
X> server { listen 80; server_name git.19.cs.nycu; return 301 https://$host$request_uri; }
X> server {
X>   listen 443 ssl; server_name git.19.cs.nycu;
X>   ssl_certificate /etc/nginx/tls/git.fullchain.crt; ssl_certificate_key /etc/nginx/tls/git.key;
X>   add_header Strict-Transport-Security "max-age=31536000" always;
X>   proxy_hide_header X-Powered-By;
X>   location / { proxy_pass http://127.0.0.1:8101; proxy_set_header Host $host;
X>     proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; proxy_set_header X-Forwarded-Proto https; }
X> }
?fill 把所有 HTTP 請求以 301 轉到 HTTPS：return 301 https://$host＿＿;
= $request_uri
E> $request_uri 包含原始路徑與 query string。
?mc HSTS（Strict-Transport-Security）的作用是？
+ 要瀏覽器之後一律用 HTTPS
- 讓伺服器的憑證有效期限延長
- 加密 HTTP header
- 防止 XSS 攻擊
E> 告訴瀏覽器在 max-age 期間內，對這個網域一律直接使用 HTTPS。可避免使用者第一次打 http:// 時被中間人攔截降級（SSL stripping）。
?mc 只設定 server_tokens off 後，回應的 Server header 會是？
+ Server: nginx（只是沒有版本號）
- 完全沒有 Server header
- Server: hidden（隱藏伺服器名稱）
- Server: off（關閉標記）
E> 要完全移除得用 headers-more 模組的 more_clear_headers。
?tf ssl_certificate 應該指向「伺服器憑證 + intermediate 憑證」串在一起的檔案。
=T
E> 用戶端只信任 root，伺服器必須送出 intermediate 才能建立完整的鏈。
?cmd 檢查 nginx 設定檔語法：
= nginx -t
= sudo nginx -t
E> 通過後再 systemctl reload nginx。

@CARD hw3.lb | NGINX 負載平衡：upstream 與 failover
A> upstream 是「排班表」：三個 IP-Srv 分身輪流接客（round-robin）。其中一個倒了，NGINX 發現連不上就把這位客人改帶到下一位，客人完全不知道（passive health check + proxy_next_upstream）。
B> TA 提供 **IP-Srv** image：容器內聽 **8000**，/ 回 JSON：**host_ip**（處理請求的 replica IP）、**client_ip**（取自 **X-Forwarded-For**）
B> IP-Srv 環境變數：IP_SRV_METRICS_USER / IP_SRV_METRICS_PASSWORD（/metrics 的 basic auth）
B> 3 個 replica 各發布 8000、8001、8002；https://{STU_ID}.cs.nycu/ 用 **round-robin** 分配
B> **任一 replica 停掉，每個請求仍要成功** → 依賴 **proxy_next_upstream**（預設 error timeout：連線失敗就換下一台）與 max_fails / fail_timeout
B> 要正確設定 **X-Forwarded-For**，IP-Srv 才回得出真正的 client IP
X> upstream ipsrv {
X>   server 127.0.0.1:8000 max_fails=1 fail_timeout=10s;
X>   server 127.0.0.1:8001 max_fails=1 fail_timeout=10s;
X>   server 127.0.0.1:8002 max_fails=1 fail_timeout=10s;
X> }
X> location / { proxy_pass http://ipsrv; proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for; }
?mc NGINX upstream 沒有指定演算法時，預設的負載平衡方式是？
+ round-robin（輪流）
- least_conn
- ip_hash
- least_conn（連線最少）
E> 可改用 least_conn、ip_hash、hash 等；也可以用 weight= 調整比例。
?mc 三個 replica 中一個被 docker stop 了，為什麼使用者的請求仍然能成功？
+ NGINX 連線失敗時會依 proxy_next_upstream 轉給下一台，並暫時標記失敗
- Docker 偵測到容器停止後，會自動把該 port 的流量改導到其他同 image 的容器
- 使用者的瀏覽器收到連線錯誤後會自動重送請求，而 Docker 也會自動重啟那個被停止的 replica，所以看起來沒有失敗
- round-robin 本身會跳過沒有在監聽的 port，不需要任何額外設定或機制
E> 預設 proxy_next_upstream error timeout；對非冪等請求（POST）預設不重試。
?fill 把 client IP 附加到 X-Forwarded-For 的 NGINX 變數是 $＿＿
= proxy_add_x_forwarded_for
E> 若原本已有 X-Forwarded-For，會在後面附加 $remote_addr。
?tf IP-Srv 回傳的 client_ip 取自 TCP 連線的來源 IP。
=F
E> 取自 X-Forwarded-For header；後端看到的連線來源永遠是 NGINX。

@CARD hw3.oidc | OIDC provider：client credentials、discovery、introspection
A> OIDC provider 是「身分證中心」。機器對機器時用 client credentials：程式拿自己的帳號密碼（client ID / secret）換一張通行證（access token），沒有真人參與。discovery 是中心門口的「服務說明牌」，寫好各窗口地址；introspection 是「打電話問中心這張證還有效嗎」，revocation 是「註銷這張證」。
B> 在 https://auth.{STU_ID}.cs.nycu 提供 OIDC provider（推薦 **Keycloak、Authentik、kanidm**）
B> 給 judge 的 **confidential client**：支援 **client credentials grant**；issuer = SA_OIDC_ISSUER，judge 用 **OIDC Discovery** 取得設定
B> Discovery：**{issuer}/.well-known/openid-configuration** → token_endpoint、jwks_uri、introspection_endpoint、revocation_endpoint…
B> access token 要能 **introspect**（RFC 7662，回 active: true/false）與 **revoke**（RFC 7009）

@CARD hw3.states | Sandbox 狀態與 Execution

@CARD hw3.falco | Syscall 監控：偵測危險行為

- 因為 syscall 監控比較省資源
- 因為 cat 不是可疑指令
E> 同一件事有無數種寫法（python、dd、less、head…），但都會產生對該檔案的 open 讀取 syscall。Detect different ways to do the same behavior。
?mt 配對行為與 rule：

- 1 筆：tmp_script（/tmp 的規則優先）
- 0 筆，因為 /tmp/nc 是複本，不是系統的 nc

@CARD hw3.otel | OpenTelemetry：Logs、Traces 與 mTLS
A> 可觀測性三兄弟：metrics 是「數字儀表板」，logs 是「流水帳」，traces 是「一次請求的完整行程表」。每段行程（span）有父子關係：API 請求是起點（SERVER），途中呼叫 Docker（CLIENT），執行任務（INTERNAL），工具呼叫又是它底下的小行程。log 帶上 trace ID，就能從流水帳跳回行程表。
B> TA **OTLP** collector：https://otel.ta.cs.nycu:**4318**（**OTLP/HTTP**；gRPC 慣例是 4317）
B> 用 **client 憑證**認證（**mTLS**）：由 intermediate 簽、**CN = {STU_ID}**、EKU 含 **clientAuth**；handshake 時送出 **client 憑證 + intermediate**
B> NGINX access log：所有主機寫到 /home/judge/hw3/logs/access.log（每請求一行），每行送成一筆 log record：**service.name=nginx**、body = 該行、sa.uri、sa.host、sa.method、sa.user_agent、sa.status（integer）；**User-Agent 為 sa-probe/{STU_ID} 的請求不記錄也不送**
B> 平台 log：service.name **llm-sandbox-platform**；事件 api_request、sandbox_status、execution_start、execution_end（INFO）、error（ERROR）；帶 **trace ID / span ID**
B> Traces：每個 API 請求一條 trace；span kind：**API request = SERVER（root）**、**Docker API call = CLIENT**、**execution = INTERNAL**（parent 是 API span，可以比它晚結束）、**tool call = INTERNAL**（parent 是 execution，從 tool_call 到同 call_id 的 tool_result）；失敗 → span status **ERROR**

X> access_log /home/judge/hw3/logs/access.log combined if=$loggable;
?mt 配對 span 與 span kind：

> 平台呼叫 Docker API :: CLIENT
> 一次 execution :: INTERNAL
> agent 的一次 tool call :: INTERNAL
E> SERVER 處理進來的請求、CLIENT 發出對外的呼叫、INTERNAL 是內部工作。
?mc 為什麼平台的 log record 要帶上 trace ID 與 span ID？

- 因為 OTLP collector 要求每一筆 log 都必須帶一個全域唯一的 ID
- 用 ID 取代重複的文字內容，可以大幅減少 log 的傳輸與儲存大小，也比較方便壓縮
E> 這叫 log 與 trace 的關聯（correlation），OTLP log record 本身就有 trace_id、span_id 欄位。
?mc 用 client 憑證連 OTLP collector 時，為什麼要連 intermediate 憑證一起送出？

- 因為 client 憑證太短，需要湊足長度
- intermediate 憑證用來加密傳送的資料
- OTLP 協定規定一定要送兩張憑證
E> collector 需要從 client 憑證建立到它信任的 root 的完整鏈；它沒有你的 intermediate。跟伺服器送 fullchain 是同一個道理。

@CARD hw3.p_openssl | 實作：用 openssl 建立 CA 與簽發憑證
A> 簽憑證的流程像辦證件：先做一把私鑰（印章）；拿私鑰填一張申請書（CSR），寫上名字與主機名；發證中心（CA）審核後蓋章，加上「用途限制」（extension），就是一張憑證。最常見的錯誤是 extension 沒帶進去，例如 SAN 不見了。
B> 私鑰：**openssl genpkey -algorithm EC -pkeyopt ec_paramgen_curve:P-256 -out x.key**（或 -algorithm RSA -pkeyopt rsa_keygen_bits:3072）；**chmod 600**
B> CSR：**openssl req -new -key x.key -subj "/CN=git.19.cs.nycu" -addext "subjectAltName=DNS:git.19.cs.nycu" -out x.csr**
B> 簽發：**openssl x509 -req -in x.csr -CA intermediate.crt -CAkey intermediate.key -CAcreateserial -days 365 -extfile ext.cnf -out x.crt**（**-extfile** 才會加入 SAN、EKU；CSR 裡的 extension 預設**不會**自動複製，可用 -copy_extensions copy）
B> 檢查：**openssl x509 -in x.crt -noout -text**、**-noout -ext subjectAltName,basicConstraints,extendedKeyUsage**
B> fullchain：**cat x.crt intermediate.crt > x.fullchain.crt**（**leaf 在前**，intermediate 在後；root 不必放）
X> # ext.cnf（伺服器憑證）
X> basicConstraints = critical, CA:FALSE
X> keyUsage = critical, digitalSignature
X> extendedKeyUsage = serverAuth
X> subjectAltName = DNS:git.19.cs.nycu
X> $ openssl x509 -req -in git.csr -CA intermediate.crt -CAkey intermediate.key -CAcreateserial -days 365 -extfile ext.cnf -out git.crt
X> $ cat git.crt intermediate.crt > git.fullchain.crt
?mc 用 openssl x509 -req 簽完的伺服器憑證，瀏覽器說沒有 SAN，但 CSR 裡明明有 -addext subjectAltName。原因？
+ 簽發時沒有帶入 extension
- SAN 只能寫在 CN 裡
- 必須使用 RSA 金鑰才有 SAN
- 瀏覽器不支援 EC 憑證
E> x509 -req 預設不會複製 CSR 的 extension，要用 -extfile 指定或加 -copy_extensions copy。簽發時由 CA 決定要放哪些 extension，這也是 CA 審核的意義。
?mc fullchain 檔中憑證的正確順序是？
+ 伺服器（leaf）憑證在最前面，接著 intermediate
- root 在最前面，接著 intermediate，最後是伺服器憑證
- root、intermediate、伺服器憑證
- 順序無所謂，用戶端會依 issuer 欄位自己排序

@CARD hw3.p_jwt | 實作：驗證 JWT access token
A> JWT 是一張「自帶防偽標記的通行證」：header 說明用哪把鑰匙簽（kid、alg），payload 寫著發給誰、誰發的、何時過期，signature 是發證單位的簽章。驗證時不能只看內容，一定要用 provider 公布的公鑰（JWKS）驗簽，並檢查發行者與期限。
B> 格式：**header.payload.signature**（各段 base64url）；payload 常見 claim：**iss**、**sub**、**aud**、**exp**、**iat**、**azp**、**scope**
B> 驗證步驟：依 header 的 **kid** 從 **jwks_uri** 取公鑰 → 驗簽章 → **iss** 等於設定的 issuer → **exp** 未過（容許少量時鐘誤差）→（需要時）**aud**
B> **alg 要固定**（例如只接受 RS256），不能相信 token 自己說的 alg（避免 alg=none 攻擊）
B> JWKS 要快取並在找不到 kid 時重新抓（provider 會輪換金鑰）
B> HTTP 慣例：沒帶或無效 token 回 **401**（WWW-Authenticate: Bearer）；token 有效但權限不夠回 **403**
X> Authorization: Bearer eyJhbGciOiJSUzI1NiIsImtpZCI6Ij...
?mc 平台驗證 JWT 時，下列哪個做法是錯的？
+ 依 token header 中的 alg 決定用什麼演算法驗證，包括 none
- 依 header 中的 kid，從 provider 的 JWKS 找出對應的公鑰
- 檢查 payload 的 iss 是否等於平台設定的 issuer 網址
- 檢查 exp 是否已過期，並容許少量的時鐘誤差
E> 驗證端要事先固定允許的演算法。
?mt 配對 HTTP 狀態碼：
> 401 :: 沒有 token 或 token 無效
> 403 :: token 有效但沒有權限
> 201 :: 成功建立資源
> 404 :: 資源不存在
E> WWW-Authenticate: Bearer error="invalid_token" 是 RFC 6750 定義的回應方式。
?mc JWT 的 payload 可以被任何人 base64 解碼讀出來。這代表？
+ JWT 只防竄改、不防偷看，不應該放機密資料
- JWT 沒有任何安全性，不應該使用
- 必須透過 HTTPS 才能解碼 payload
- 簽章也可以被解碼，算出私鑰
E> 安全性來自簽章；內容是公開的。

B> CI 端：**known_hosts 預先放 host 的公鑰**，用 StrictHostKeyChecking=yes，避免被中間人冒充
B> 能執行 docker 等於 root：部署帳號的能力要靠 forced command 限縮

X> tag=$SSH_ORIGINAL_COMMAND

- 只允許從某個 IP 登入
- 讓 key 不需要密碼

@CARD hw3.p_dockerapi | 實作：平台透過 Docker API 管理 sandbox
A> 平台跟 Docker 溝通不是打 docker 指令，而是對 /var/run/docker.sock 送 HTTP 請求（Docker Engine API），或用 SDK 包好的函式。建立、啟動、執行指令、查結果、刪除，都有對應的 API。
B> 以 HTTP over unix socket：**curl --unix-socket /var/run/docker.sock http://localhost/containers/json**
B> 生命週期：**POST /containers/create**（Image、Env、HostConfig：Binds/Mounts、NetworkMode、Dns、CapDrop、Memory、PidsLimit）→ **POST /containers/{id}/start** → **POST /containers/{id}/stop** → **DELETE /containers/{id}?force=true**
B> 執行指令：**POST /containers/{id}/exec**（Cmd、WorkingDir=/workspace、AttachStdout/Stderr）→ **POST /exec/{id}/start**（串流輸出）→ **GET /exec/{id}/json**（Running、**ExitCode**）
B> Tty=false 時輸出是**多工串流**：每段前面 8 bytes header（第 1 byte 1=stdout、2=stderr，最後 4 bytes 為長度）；要「依序合併」就讓指令自己 **2>&1**
B> exec **沒有 stop API**：要停止 execution，得找出它的 process 再送訊號（例如記下 PID、用另一個 exec 對 process group 送 SIGTERM）
B> Docker API 呼叫會形成 CLIENT span，名稱如 **POST /containers/create**
X> curl -s --unix-socket /var/run/docker.sock -X POST -H 'Content-Type: application/json' \
X>   -d '{"Image":"sandbox:latest","HostConfig":{"Binds":["sbx-123-ws:/workspace"],"PidsLimit":256}}' \
X>   'http://localhost/containers/create?name=sbx-123'
X> # 依序合併 stdout/stderr，並避免引號問題
X> ["sh","-c","exec bash -c \"$1\" 2>&1","_","<使用者的 input>"]
?mc 用 exec API（Tty=false）讀到的原始輸出開頭有奇怪的位元組。原因？
+ 輸出帶有 8-byte 多工 header
- 輸出被 Docker 用 gzip 壓縮過
- 容器的語系設定與 host 不同
- 需要改用 HTTP/2 才能正確讀取
E> Docker 用 8-byte header 多工 stdout 與 stderr，需要解析 header 才是真正內容。SDK（如 docker-py 的 demux）會幫你處理；Tty=true 不會多工，但會把 \n 轉成 \r\n。
?mc 要取得某次 execution 的 exit code，應該呼叫？
+ GET /exec/{id}/json，讀 ExitCode（Running 為 false 時）
- GET /containers/{id}/logs，從最後一行輸出解析 exit code
- POST /exec/{id}/stop 停止 exec，回應中會包含它的 exit code
- GET /containers/json 列出容器時，每個 exec 的結果都在裡面
E> Running 為 true 時 ExitCode 還沒有意義（execution 狀態應為 running、exit_code 為 null）。
?mc 為什麼把使用者的 input 當成 sh -c 'exec bash -c "$1" 2>&1' _ "<input>" 的參數，而不是字串拼接成指令？
+ 以參數傳遞不需要處理引號跳脫，input 中的引號或特殊字元不會破壞外層指令
- 這樣執行比較快，因為 bash 不需要重新解析整個指令字串
- bash 的 -c 參數不接受超過 100 個字的字串，所以要用位置參數
- Docker 的 exec API 規定指令一定要用這種格式傳入
E> $1 是第一個位置參數；_ 佔住 $0。

@CARD hw3.p_lifecycle | 實作：pause / resume 與平台的優雅關機
A> 平台關機時要「先幫每個房客收拾工作桌」：停掉正在跑的 execution、保留 /workspace、刪掉容器、狀態改成 paused。這些動作需要時間，所以 compose 給平台的關機寬限期要夠長，平台也要接住 SIGTERM 才有機會做事。
B> /workspace 放在**每個 sandbox 一個 volume**（例如 sbx-<id>-ws）；容器名稱帶 sandbox_id，ID 本身存資料庫、pause/resume 不變
B> pause：stop 執行中的 execution（狀態 **stopped**，保留已產生的輸出）→ 刪除容器（**不刪 volume**）→ paused
B> resume：用同一個 image 與 volume **建立新容器**、套用相同的網路與環境變數 → running
B> close：刪除容器**與 volume** → closed
B> 平台收到 **SIGTERM** 時 pause 所有 running sandbox；compose 設 **stop_grace_period: 60s**（預設 10 秒可能不夠）；重啟後**不自動 resume**
B> 啟動時對帳：資料庫說 running、但容器不存在的 sandbox 要修正狀態
X>   platform:
X>     stop_grace_period: 60s
X>     volumes:
X>       - /var/run/docker.sock:/var/run/docker.sock
X> # Python：接住 SIGTERM
X> signal.signal(signal.SIGTERM, lambda *_: pause_all_and_exit())
?mc docker compose down 時，平台來不及 pause 所有 sandbox 就被殺掉。最可能的原因？
+ 預設寬限期只有 10 秒
- 平台沒有掛 docker.sock
- volume 太大
- 平台用的是 alpine image
E> 預設只等 10 秒就送 SIGKILL，要調高 stop_grace_period，並確保程式有處理 SIGTERM。若 CMD 是 shell form，平台甚至收不到 SIGTERM（PID 1 問題）。
?mc resume 時為什麼不用 docker start 重新啟動原本的容器？
+ pause 時容器已被刪除；規格要求 resume 建立新容器，只有 /workspace 保留
- docker start 不能用在掛了 volume 的容器，否則 /workspace 會被清空
- 原本的容器 ID 會和新的 sandbox_id 衝突，資料庫寫不進去
- docker start 需要 root 權限，而平台容器裡沒有 root
E> 新容器會有新的 container ID，所以資料庫要用自己的 sandbox_id 追蹤。
?tf close 一個 sandbox 時，應該連 /workspace 的 volume 一起刪除。
=T
E> Close：Delete the container and the kept content。

@CARD hw3.p_sbxnet | 實作：怎麼讓 sandbox 的流量只能走平台
A> 讓 sandbox 住在一座「只有一座橋的島」上：島（internal 網路）本身不通外面，唯一的橋就是平台容器。sandbox 的預設路由和 DNS 都指向平台；平台不幫忙轉送封包，只把 80、443、53 的連線「攔下來交給自己的 proxy 和 DNS」，其他封包自然就到不了任何地方。
B> sandbox 只接 **internal 網路**（沒有對外路由）；平台同時接 internal 網路與一般網路
B> DNS：建立容器時 **Dns=[平台 IP]**；預設路由：由有 NET_ADMIN 的輔助容器 **--network container:<sbx>** 執行 **ip route replace default via 平台 IP**（sandbox 本身沒有 NET_ADMIN 改不回來）
B> 平台容器（需 **NET_ADMIN**）：**ip_forward 關閉**（不轉送）；iptables **REDIRECT** 把 tcp/80、tcp/443 導到 HTTP / HTTPS proxy，udp+tcp/53 導到 DNS
B> 其他流量：沒有被 REDIRECT、也不轉送 → 被丟棄（也可明確 DROP）
B> proxy 依 Host / SNI 自己用平台 DNS 解析再連線；用來源 IP 對應到 sandbox_id 以記錄事件
X> # 平台容器內
X> sysctl -w net.ipv4.ip_forward=0
X> iptables -t nat -A PREROUTING -i eth1 -p tcp --dport 80  -j REDIRECT --to-ports 8080
X> iptables -t nat -A PREROUTING -i eth1 -p tcp --dport 443 -j REDIRECT --to-ports 8443
X> iptables -t nat -A PREROUTING -i eth1 -p udp --dport 53  -j REDIRECT --to-ports 5353
?mc 平台容器把 ip_forward 關閉的目的？
+ 不替 sandbox 轉送封包
- 讓 DNS 查詢變快
- 防止平台被 OOM kill
- 讓 sandbox 可以直接上網
E> 平台不會替 sandbox 轉送任何封包，只有被 REDIRECT 給 proxy / DNS 的連線能出去。所有對外連線都必須由平台的程式代為發出，才能檢查與記錄。
?mc iptables 的 REDIRECT 目標做了什麼？
+ 把連線導到本機的 port
- 把封包丟棄
- 把封包轉送到另一台主機
- 加密封包
E> 把封包的目的地改成本機的指定 port，讓本機程式（proxy）接手這條連線。透明代理的常見做法，用戶端不需要設定 proxy。
?mc 平台如何知道某個連線來自哪個 sandbox？
+ 依連線的來源 IP
- 依 HTTP User-Agent
- 依 TLS 的 SNI
- 依 DNS 查詢的內容
E> 依連線的來源 IP，對照每個 sandbox 容器在 internal 網路上的 IP。建立容器後用 inspect 取得 IP，存進對照表。

@CARD hw3.p_mitmimpl | 實作：HTTPS 攔截 proxy 的流程
A> 攔截 HTTPS 的順序很重要：先偷看信封上的收件人（ClientHello 的 SNI），檢查名單、去真正的網站驗證身分與黑名單；確認沒問題，才用自己的印章臨時做一張該網站的證件給 sandbox。上游驗證失敗，就直接在握手時回一個 TLS alert 拒絕。
B> ① 讀 **ClientHello 的 SNI**（還沒解密）→ 不在 allowlist、或是 IP → 記錄 block event 並斷線
B> ② 用平台 DNS 解析 SNI、連到真網站，以 **VM 信任的 CA**（例如掛入 host 的 /etc/ssl/certs/ca-certificates.crt）驗證憑證鏈與主機名
B> ③ 檢查撤銷：從憑證的 **CRL Distribution Points** 下載 CRL、**每 60 秒內更新**、檢查**整條鏈**（Python：**ssl.VERIFY_CRL_CHECK_CHAIN** 並載入 CRL）
B> ④ 通過後，以**攔截 CA** 即時簽一張 **SAN = SNI** 的憑證（依 SNI 快取），完成與 sandbox 的握手；失敗則送 **TLS alert** 並記錄 tls_invalid / tls_revoked
B> ⑤ 解密後逐一轉送 request：同一條連線上的**每個 request 各記一筆 event**；body 去掉 chunked、保留 Content-Encoding、base64
?ord 攔截一條 sandbox 的 HTTPS 連線，合理的處理順序：
> 讀取 ClientHello 中的 SNI 並檢查 allowlist
> 解析 SNI、連到真網站並驗證憑證與 CRL
> 以攔截 CA 簽發 SAN 為該網域的憑證，完成與 sandbox 的握手
> 轉送並記錄每一個 HTTP request 與 response
E> 先驗上游，才能在上游有問題時，用 TLS alert 拒絕 sandbox。
?mc 為什麼平台要用「VM 信任的 CA」來驗證真網站，而不是 sandbox 裡的 CA？
+ sandbox 的信任清單可被竄改
- sandbox 裡沒有任何 CA
- VM 的 CA 比較新
- 規格沒有理由
E> sandbox 可以被 agent 任意修改（例如加入惡意 CA），平台的判斷不能依賴它。平台是信任邊界，要用自己可控的信任清單。
?mc CRL 是什麼？
+ 已撤銷憑證的清單
- 憑證的申請檔
- 加密用的對稱金鑰
- DNS 的記錄類型

@CARD hw3.p_spans | 實作：span 的父子關係與時間
A> 一條 trace 是一次 API 請求的「行程表」。API 請求是起點（root span），途中每個 Docker 呼叫是它的子行程；execution 是背景任務，雖然是 API 請求派出去的（所以是它的子 span），但可以比 API 請求晚很多才結束；tool call 的起訖時間則來自 sallm-cli 事件裡的 time。
B> 每個 API 請求一條 trace：root span 名稱 = **方法 + route 樣板**（POST /api/sandboxes/{id}/executions，**不要**放實際 ID，避免基數爆炸）
B> Docker 呼叫：**CLIENT** span，名稱 **POST /containers/create** 等，parent 是發出呼叫的 span
B> execution：**INTERNAL** span，parent 是 API span，**可以比 parent 晚結束**（背景執行時要把 context 傳到背景工作）
B> tool call：從 tool_call 到相同 **call_id** 的 tool_result，**用事件中的 time 設定 start / end time**
B> 失敗：span status **ERROR**（並記錄例外）；log 帶 trace_id / span_id 對應產生它的 span

- 因為實際的 sandbox ID 是機密，不能出現在 trace 中
- 因為 OpenTelemetry 規定 span 名稱不能包含數字或連字號
- 為了讓 trace 比較短，放 ID 會讓每個 span 名稱超過長度上限
E> 實際 ID 放在 lmsp.sandbox_id attribute。

- 跟 API span 一起結束
- 另開一條新的 trace
- 不需要 span
E> 仍以 API span 為 parent，在 execution 真正結束時才結束。規格：The execution span lasts from start to end and can end after the API request span。
