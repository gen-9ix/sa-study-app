@CARD shell.layers | Terminal、Shell、Kernel
A> 餐廳：Terminal 是「菜單和桌子」（顯示文字、收你的按鍵）、Shell 是「點餐服務生」（聽懂你的話、展開縮寫、幫你下單）、Kernel 是「廚房」（真正管 process、記憶體、裝置）。
B> **Terminal**：使用者介面，顯示文字並送出按鍵
B> **Shell**：跑在 terminal 裡的**程式**；解析指令、展開變數與 pattern，再執行 built-in 或外部程式
B> **Kernel**：管理 process、memory、devices，提供 system call
?mt 配對角色：
> Terminal :: 顯示文字、傳送按鍵的介面
> Shell :: 解析語法、展開變數並啟動程式
> Kernel :: 管理 process、記憶體與裝置
E> Shell 只是 terminal 裡的一支程式，不是 terminal 本身。
?tf Shell 和 terminal 是同一個東西的兩種叫法。
=F
E> Terminal 是介面；shell 是在 terminal 裡執行的程式（例如 bash、tcsh）。

@CARD shell.enter | 按下 Enter 之後發生什麼事
A> 服務生收到點單後的流程：先讀懂（parse）→ 把「老樣子」換成實際菜名（expand）→ 判斷這道菜是吧台自己做還是送廚房（resolve）→ 下單（execute）→ 決定你要等著吃還是先去逛（前景/背景）。
B> ① **Read & parse**：引號、operator、redirection
B> ② **Expand**：變數、$(...)、wildcard
B> ③ **Resolve**：built-in？function？還是在 PATH 裡找
B> ④ **Execute**：built-in 直接做，或 **fork/exec** 外部程式
B> ⑤ **Wait / manage job**：前景或背景
B> 重點：**shell 會在大多數外部程式看到參數之前就先處理好語法**
X> $ ls "$HOME"/*.txt | grep report > matches.txt 2> errors.txt
?ord 依序排列 shell 處理指令的步驟：
> Read & parse（引號、operator、redirection）
> Expand（變數、$(...)、萬用字元）
> Resolve（built-in / function / PATH）
> Execute（built-in 或 fork/exec）
> Wait / 管理 job（前景或背景）
E> 所以 ls *.txt 的 * 是 shell 展開好才交給 ls 的，ls 根本看不到星號。
?tf 執行 ls *.txt 時，是 ls 程式自己去展開 *.txt。
=F
E> 是 shell 在執行前就展開（globbing），ls 收到的是展開後的檔名清單。

@CARD shell.kinds | 常見 Shell 與預設值
A> 不同 shell 像不同方言：sh 是「普通話」（POSIX，寫腳本最通用）、bash 是 Linux 上最常見的口語、zsh 是 macOS 的預設、tcsh 是 BSD 老派方言、PowerShell 是物件導向的外國話。
B> **sh**（/bin/sh）：POSIX Bourne 風格，**寫可攜腳本的基準**
B> **bash**：Bourne Again Shell，Linux 常見互動 shell
B> **zsh**：macOS 預設 login shell
B> **tcsh**：C shell 家族，BSD/舊環境常見
B> **PowerShell**（pwsh）：物件導向自動化 shell，跨平台
B> 預設：Debian 新使用者多為 bash（/bin/sh 是另一個 POSIX shell，Debian 上是 dash）；FreeBSD 14+ 一般使用者與 root 都是 sh，bash 不在 base system；macOS zsh
B> 查詢：getent passwd "$USER" 看設定的 login shell；echo "$SHELL" 只是提示
?mc 寫要在 Debian 與 FreeBSD 都能跑的腳本，最適合指定哪個 shell？
+ /bin/sh（POSIX sh）
- /bin/bash（Linux 預設）
- /bin/tcsh（FreeBSD 預設）
- /bin/zsh（功能最多）
E> FreeBSD base system 沒有 bash；POSIX sh 是可攜的基準。
?tf 在 FreeBSD 14 的 base system 中預設就有 bash。
=F
E> bash 不在 FreeBSD base system，要另外 pkg install。

@CARD shell.modes | Login / Interactive / Non-interactive
A> 三種上班方式：「打卡進公司」(login shell) 會先看公告欄 (.profile)；「已經在公司裡又開了一個新分頁」(interactive non-login) 看自己桌上的便利貼 (.bashrc)；「派機器人去做事」(non-interactive，跑腳本) 通常什麼都不看。
B> **Interactive login**：console 登入、ssh 登入 → 讀 login 啟動檔
B> **Interactive non-login**：開新 terminal 分頁、在 shell 裡再打 bash → 讀 rc 檔
B> **Non-interactive**：執行腳本 ./backup.sh → 通常**不讀** interactive rc 檔
B> 常見錯誤：只把腳本需要的變數放在 ~/.bashrc → 在 **cron、SSH 自動化、systemd** 下行為不同

- cron 的 shell 是 sh，不支援 export 這個語法
- export 只在 root 身分下有效
- ~/.bashrc 只有 zsh 才會讀取
E> cron 跑的是 non-interactive shell，通常不會讀 ~/.bashrc。腳本需要的變數應在腳本內設定，或在 crontab 中設定。
?mc 用 ssh 登入遠端主機得到的 shell 通常是哪一種？
+ Interactive login shell
- Interactive non-login shell
- Non-interactive shell
- Subshell

@CARD shell.startup | Bash / sh / tcsh 啟動檔
A> Bash 的 login shell 在三本日記（~/.bash_profile、~/.bash_login、~/.profile）中只讀「第一本找得到的」，所以常在 .bash_profile 裡寫一句「也去讀 .bashrc」。
B> Bash **interactive login**：/etc/profile → 再讀 ~/.bash_profile、~/.bash_login、~/.profile 中**第一個可讀的**
B> Bash **interactive non-login**：~/.bashrc
B> Bash **non-interactive**：$BASH_ENV 指定的檔（若有設）
B> Login shell 結束：~/.bash_logout
B> 常見做法：~/.bash_profile 去 source ~/.bashrc
B> FreeBSD **sh**：login 讀 ~/.profile；interactive 讀 $ENV 指定的檔
B> **tcsh**：~/.tcshrc 或 ~/.cshrc（interactive）；~/.login / ~/.logout（login/logout）
B> 安全編輯：先讀再改、先備份、開新 shell 或 source 套用；不要 curl | sh（應下載、檢查、驗證後再執行）
?mt 配對 bash 情境與讀取的檔案：
> Interactive login shell :: /etc/profile + ~/.bash_profile（或 .bash_login / .profile 第一個可讀的）
> Interactive non-login shell :: ~/.bashrc
> Non-interactive shell :: $BASH_ENV 指定的檔
> Login shell 結束時 :: ~/.bash_logout
E> 這是 GNU Bash 手冊「Bash Startup Files」的內容。
?tf 同時存在 ~/.bash_profile 和 ~/.profile 時，bash login shell 兩個都會讀。
=F
E> 只讀「第一個可讀的」，所以有 .bash_profile 時 .profile 會被忽略（除非手動 source）。
?mc 為什麼不建議用 curl https://x.sh | sh 安裝軟體？
+ 跳過了「下載 → 檢查 → 驗證來源」的步驟，直接執行遠端內容
- 因為 curl 無法下載副檔名是 .sh 的檔案
- 因為 sh 不能從 stdin 讀取指令，只能讀檔案
- sh 執行 pipe 傳進來的內容時，會自動以 root 權限執行，非常危險
E> 應先下載、檢查內容、確認來源，再執行。

@CARD shell.envvar | Shell 變數 vs 環境變數、PATH
A> Shell 變數是「寫在自己筆記本上的事」，只有自己看得到；export 之後變成「交代給小孩的家訓」，之後生的小孩（child process）都會繼承一份「影本」，小孩改影本不影響爸媽，已經出生的小孩也拿不到新家訓。
B> **Shell 變數**：name=alice，只在目前 shell 可見，**不會**自動傳給 child
B> **環境變數**：export EDITOR=vim，之後啟動的 **child process 會繼承**
B> env / printenv 看環境變數；set 可看 shell 變數
B> 常用：HOME、USER/LOGNAME、**SHELL**（設定的 login shell，不一定是目前執行的 shell）、**PATH**（以冒號分隔的指令搜尋目錄）、PWD、EDITOR/VISUAL、LANG/LC_*
B> **PATH 從左往右找**，找到第一個就執行
B> 環境變數只存在 **process 記憶體**中，重開機/登出就沒了；要永久 → 寫進啟動檔（~/.profile、~/.bashrc，或系統層 /etc/profile）
?sa 有時我們會使用指令 export PATH="$PATH:/usr/local/sa/bin"，請回答：a. 執行前後的行為差異 b. 若在 process A 執行，除了 A 還有哪些 process 的 $PATH 被更新？ c. 重開機後 $PATH 是哪種狀態？為什麼？ d. 怎麼讓它永久保存？ e. 改成 export PATH="/usr/local/sa/bin:$PATH" 有何差異？
S> 2025 期末 Q10
R> a. 執行後 /usr/local/sa/bin 被加到搜尋路徑最後面，直接打指令名稱時也會到該目錄找（但優先順序最低）。
R> b. 只有之後由 process A 建立的 child process（及其後代）會繼承新的 PATH；A 的 parent、其他已在執行的 process 都不受影響。
R> c. 回到 export 之前的狀態，因為環境變數只存在 process 的記憶體中，重開機後所有 process 重新啟動，不會保留。
R> d. 把這行寫進啟動檔，例如 ~/.profile 或 ~/.bashrc（個人），或 /etc/profile、/etc/profile.d/*.sh（全系統），登入時就會自動執行。
R> e. 放在前面 → 優先搜尋 /usr/local/sa/bin，若有與系統指令同名的程式會「蓋過」系統版本；放後面則系統指令優先。放前面若該目錄可被他人寫入有安全風險。
P> a. 加到 PATH 尾端，可直接執行該目錄指令
P> b. 只有之後產生的 child process 會繼承
P> c. 回到原狀，環境變數只在記憶體中
P> d. 寫入 ~/.profile / ~/.bashrc 等啟動檔
P> e. 前面優先搜尋，會覆蓋同名指令
?sa 撰寫 Bourne Shell (/bin/sh) 腳本時，直接使用 var=value 與使用 export var=value、local var=value 有何差別？
S> 2023 期中 Q3
R> var=value：一般 shell 變數，只在目前 shell（含其 function）中可見，不會傳給 child process。
R> export var=value：設為環境變數，之後由此 shell 啟動的 child process 都會繼承一份副本。
R> local var=value：只在目前 function 內有效（function 結束就消失，也不會影響外面同名變數）；local 不是 POSIX 標準，但 dash、bash 等多數 sh 實作支援。
P> 一般變數只在目前 shell
P> export 會被 child process 繼承
P> local 限定在 function 範圍內
?sa 試舉出三個 Unix 系統預先定義的環境變數，並說明用途。
S> 2023 期中 Q7
R> HOME：使用者家目錄路徑（cd 不加參數就回到這裡）。
R> PATH：以冒號分隔的目錄清單，shell 依序在這些目錄中尋找要執行的指令。
R> SHELL：使用者設定的 login shell 路徑。
R> 其他可答：USER/LOGNAME（使用者名稱）、PWD（目前目錄）、EDITOR（預設編輯器）、LANG（語系）、TERM（終端機類型）。
P> 正確舉出三個變數名
P> 每個都說明正確用途
?mc 小明在 shell A 中 export FOO=1，接著在 A 裡執行 bash 進入 shell B，再在 B 中 export FOO=2 後 exit 回到 A。此時 A 的 echo $FOO 會是？

=F

@CARD shell.assign | 變數設定與展開
A> sh 的等號很「黏」：name=value 中間不能有空白；有空白時 shell 會以為你要執行一個叫 name 的指令。
B> POSIX：course=sa、month=$(date +%m)、export EDITOR=vim
B> tcsh：set course=sa、set month=`date +%m`、**setenv EDITOR vim**
B> sh/bash 的簡單賦值 **= 兩邊不能有空白**
B> 除非刻意要 field splitting / 路徑展開，否則**展開時加雙引號**："$var"
B> 新程式優先用 **$(command)** 而非反引號
?mc 在 sh 中執行 name = alice 會發生什麼？
+ 把 name 當成指令執行而失敗
- 成功把 alice 指定給 name
- 把 name 設成空字串
- 產生語法錯誤並結束 shell
E> shell 把 name 當成指令名稱，參數為 = 與 alice，通常出現 command not found。賦值時等號兩邊不能有空白。
?cmd 在 tcsh 中設定環境變數 EDITOR 為 vim：
= setenv EDITOR vim
E> tcsh 用 setenv（環境變數）與 set（shell 變數）。

@CARD shell.quote | 引號規則
A> 單引號是「保鮮膜」：裡面的東西原封不動，$ 也不會被打開；雙引號是「透明袋」：看得到裡面，$var 和 $(...) 會被替換，但空白不會被拆開；沒加引號就是「散裝」，可能被拆開（field splitting）又被當萬用字元展開。
B> **'text'**：全部字面，不做參數/指令替換 → echo '$HOME' 印出 $HOME
B> **"text"**：參數與指令替換仍會發生 → echo "$HOME" 印出路徑
B> **\**：跳脫下一個字元 → echo \*
B> **不加引號**：可能發生 field splitting 與 pathname expansion → 危險
B> 預設習慣：變數展開一律加雙引號 "$var"
?sa 假設某目錄有三個檔案，以 /bin/sh 執行下列兩行。若再執行 echo 'Result: $var' 的結果為何？
QX> $ /bin/ls
QX> a1 b2 c3
QX> $ var=`/bin/ls`
S> 2023 期中 Q1
R> 輸出為 Result: $var（字面上的 $var）。
R> 因為使用單引號，單引號內的所有字元都是字面意義，不會做變數展開；雖然 var 已存有 ls 的輸出，但不會被替換。若改用雙引號 echo "Result: $var" 才會印出檔名。
P> 輸出 Result: $var
P> 單引號內不做變數展開

+ /home/amy $HOME
- /home/amy /home/amy
- $HOME $HOME
- $HOME /home/amy
E> 雙引號會展開，單引號不會。
?tf 雙引號 "..." 裡的 $(date) 仍然會被執行並替換。
=T
E> 雙引號內參數替換與指令替換都會發生。

@CARD shell.cmdsub | 指令替換 $(...)
A> $(command) 像「把小幫手做完的結果貼在這裡」：先執行括號裡的指令，再把它的 stdout 塞回原位（尾端換行會被剪掉）。
B> **$(command)** 用指令的 stdout 取代整個運算式
B> 尾端的換行會被移除
B> $(...) 可以乾淨地巢狀，比反引號 `...` 好讀
B> POSIX 兩種都支援，新程式優先用 $(...)
X> now=$(date)
X> count=$(wc -l < /etc/passwd)
X> archive="$(basename "$(pwd)").tar.gz"
?tf 指令替換 $(cmd) 會保留輸出尾端的換行字元。
=F
E> 尾端換行會被移除。
?mc 為什麼新的 sh/bash 程式建議用 $(...) 而不是反引號？
+ 可以乾淨地巢狀，也比較好讀
- 反引號在 POSIX 中不合法
- $(...) 執行比較快
- 反引號只能在 tcsh 使用
E> 兩者 POSIX 都支援，但 $(...) 巢狀不用跳脫。

@CARD shell.glob | 路徑展開 (Globbing)
A> Glob 是「選檔名的萬用牌」：* 是任意長度鬼牌、? 是一張鬼牌、[12] 是「只能是 1 或 2」。它比正規表達式陽春，而且是 shell 在執行前就翻好牌。
B> **\***：任意字串（包含空字串）→ ls test* 符合 test1 test2 test-5 testmess
B> **?**：任意**單一**字元 → test?
B> **[abc]**：集合中的一個字元；**[!abc]**：不在集合中的一個字元
B> **不是 regex**！要讓程式（而非 shell）解讀 pattern 時，要加引號
?mc 目錄中有 test1、test2、test-5、testmess，執行 ls test? 會列出？
+ test1 test2
- test1 test2 test-5
- 全部四個
- testmess
E> ? 只代表剛好一個字元。
?mc 在 glob 中，「不屬於集合 a、b、c 的一個字元」怎麼寫？
+ [!abc]
- [^abc]（這是 regex 寫法）
- !(abc)
- [-abc]
E> POSIX glob 用 [!...]；regex 才用 [^...]。

@CARD shell.ctrl | 控制運算子與 Exit Status
A> Exit status 是指令交的成績單：0 分代表「沒問題」（跟一般考試相反！），非 0 代表出事。&& 是「考過了才繼續」、|| 是「考爛了才補救」、; 是「不管考幾分都繼續」。
B> **;**：不管結果都執行下一個（cd /tmp; pwd）
B> **&&**：前一個**成功**才執行（make && make test）
B> **||**：前一個**失敗**才執行（mkdir out || exit 1）
B> 慣例：**exit status 0 = 成功**，非 0 = 失敗或特殊狀況；$? 查看上一個指令的狀態
X> $ false; echo $?
X> 1
X> $ true; echo $?
X> 0
?mc 執行 false && echo A || echo B 會輸出？
+ B
- A
- A 與 B
- 沒有輸出
E> false 失敗 → 跳過 && 的 echo A → 整體失敗 → 執行 || 的 echo B。
?fill 慣例上，指令執行成功時 exit status 為＿＿
= 0
E> 0 成功，非 0 失敗。

@CARD shell.bg | 跳脫、續行與背景執行 &
A> & 是「叫外送」：下單後你不用在門口等，可以繼續做事；但外送員還是記得你的地址（terminal），所以不等於「完全斷開關係」。
B> **\** 跳脫特殊字元（touch test\*），或放在行尾讓指令**續行**
B> **&**：在 interactive shell 把指令當**背景 job** 啟動
B> 背景 ≠ 脫離（detached）：terminal 訊號與輸出仍可能有影響
B> 長期服務應交給 **systemd / rc.d / supervisor**，不要靠 &
B> $! = 最近一個背景 process 的 PID
?sa a. 解釋指令 sleep 10 &。 b. 在下列操作中，該 sleep process 會發生什麼事？請解釋原因。
QX> $ ssh my-host
QX> [user@my-host] $ echo $SHELL
QX> /bin/bash
QX> [user@my-host] $ sleep 10 &
QX> [user@my-host] $ exit
S> 2025 期末 Q2
R> a. sleep 10 & 讓 shell fork 出 sleep process 並放到背景執行（成為一個 job），shell 不等它結束，立刻回到提示字元；sleep 會睡 10 秒後結束。
R> b. 用 exit 正常登出時，bash 預設 huponexit 是關閉的，所以不會送 SIGHUP 給背景 job。sleep 的 parent（bash）結束後它變成 orphan，被 PID 1（systemd）或 subreaper 收養，繼續執行直到 10 秒後正常結束並被收屍。
R> 補充：若是 ssh 斷線 / 關閉終端，bash 收到 SIGHUP 會把 SIGHUP 轉送給所有 job，sleep（預設動作 terminate）就會被終止；若設了 shopt -s huponexit，或 systemd-logind 設定 KillUserProcesses=yes，exit 時也會被終止。若想確保不被 SIGHUP 影響可用 nohup 或 disown。
P> a. & 讓 sleep 在背景執行，shell 不等待
P> b. bash 預設 huponexit off，exit 不送 SIGHUP

@CARD shell.builtin | Built-in vs 外部指令
A> Built-in 是服務生「自己動手」做的事（在 shell process 裡做），所以能改變 shell 本身的狀態；外部指令要「送廚房」（fork 一個新 process），廚房改了什麼都影響不到服務生。所以 cd 一定是 built-in，如果 cd 是外部程式，它只會改到廚房的位置，你人還在原地。
B> **Built-ins**：cd、export、alias、jobs、fg、bg、exit，**在 shell process 內執行**，可以修改 shell 狀態
B> **外部指令**：ls、grep、awk、sort、ssh、python，透過 PATH 或明確路徑找到，以**獨立 process** 執行
B> 查詢：**type cd** → cd is a shell builtin；**command -V grep** → grep is /usr/bin/grep
?mc 為什麼 cd 必須是 shell built-in？
+ 外部程式在 child process 改目錄，不會影響 parent shell 的工作目錄
- 因為 cd 太常用，做成 built-in 可以省下每次 fork 與 exec 外部程式的時間
- 因為切換目錄需要 root 權限，只有 shell 本身有這個權限，外部程式沒有
- PATH 裡的外部 cd 不能處理含空白的路徑，所以 bash 另外內建一個版本
E> child 的狀態改變不會傳回 parent，所以會改變 shell 狀態的指令必須是 built-in。
?cmd 查詢 cd 是 built-in 還是外部指令：
= type cd
= command -V cd
E> type 或 command -V。

@CARD shell.fd | 標準串流與 File Descriptor

B> **0 = stdin**：預設鍵盤 / 呼叫者
B> **1 = stdout**：預設 terminal
B> **2 = stderr**：預設 terminal（錯誤訊息）
M> 0 進 1 出 2 錯

> 1 :: stdout
> 2 :: stderr

= 2
E> 0 stdin、1 stdout、2 stderr。

- 因為 stdout 只能寫入檔案，錯誤訊息需要另一條路顯示

@CARD shell.redir | Redirection 與 2>&1
A> 2>&1 的意思是「把 2 號水管接到 1 號水管**現在**接的地方」。所以順序很重要：先把 1 接到檔案再接 2（>out 2>&1）→ 兩個都進檔案；如果先 2>&1 再 >out → 2 接到的是「1 原本的地方（螢幕）」。
B> **cmd < file**：file 當 stdin
B> **cmd > file**：stdout 寫入檔案（先清空 truncate）
B> **cmd >> file**：stdout 附加 (append)
B> **cmd 2> file**：stderr 寫入檔案
B> **cmd > out 2>&1**：stdout 與 stderr 都進同一個檔
B> **2>&1 = 讓 fd 2 指向 fd 1「此刻」指向的地方**；由左到右處理，**順序會影響結果**
B> printf ... >&2：把訊息送到 stderr
?sa 請解釋 echo "2025 SA Final" 2>&1 中的 2>&1 代表什麼。

R> 在這個例子中 stdout 本來就是 terminal，所以 stderr 也指向 terminal，輸出看起來沒有差別（echo 也沒有錯誤輸出）；它常和 > file 一起用，如 cmd > log 2>&1 把兩者都寫進檔案，且順序重要。

P> 把 stderr 導向 stdout 目前指向的位置
P> （加分）此例中兩者都指向 terminal / 順序重要

@CARD shell.p_find | 實作：find 把檔案找出來
A> find 是「拿著條件清單逐間搜房間的搜查員」：你給起點目錄和條件（名字、類型、大小、時間、擁有者、權限），它一層層走進去比對。HW2 一開機就要用它：initramfs 被藏在 /root 底下，先找到才修得了。

B> 常用條件：**-name / -iname**（檔名）、**-type f / d / l**、**-size +100M**、**-mtime -1**（一天內改過）、**-user judge**、**-perm -4000**（含 setuid）
B> 動作：預設印出路徑；**-delete** 刪除；**-exec cmd {} \;** 每個檔跑一次、**-exec cmd {} +** 盡量湊成一次

B> 只想查「指令在哪」用 `command -v` 或 `which`，不必 find
X> find /root -type f -name 'initrd.img*'
X> find / -type f -perm -4000 2>/dev/null        # 全系統 setuid 檔
X> find /var/log -name '*.log' -size +50M -exec ls -lh {} +
X> find /tmp -type f -mtime +7 -delete
?cmd 在 /root 底下找出檔名以 initrd.img 開頭的檔案：
= find /root -name 'initrd.img*'
= find /root -type f -name 'initrd.img*'
= find /root -name "initrd.img*"
E> pattern 加引號，交給 find 自己比對。
?mc `find . -name '*.sh' -exec chmod +x {} \;` 與結尾改成 `{} +` 的差別是？
+ `\;` 每找到一個檔就執行一次指令；`+` 把多個檔名湊在一起、執行次數少
- `\;` 只處理找到的第一個檔案；`+` 會把找到的全部都處理
- `\;` 會在每個檔名前後加上引號；`+` 不加引號，所以檔名有空白時會出錯
- 兩者完全相同，`+` 只是新版 find 為了好打字加入的寫法
E> `+` 的行為類似 xargs，檔案多時快很多。
?cmd 找出整個系統中帶有 setuid 位元的一般檔案，並把錯誤訊息丟掉：

= find / -perm -4000 -type f 2>/dev/null
E> -perm -4000 表示「至少含有」setuid 位元。
?tf `find /etc -name *.conf`（pattern 沒加引號）在任何目錄下執行，結果都和加了引號一樣。
=F
E> 若目前目錄剛好有 .conf 檔，shell 會先把 *.conf 展開成那些檔名，find 收到的條件就變了。

@CARD shell.p_which | 實作：command not found 怎麼查
A> shell 找指令像「照 PATH 這張清單一間一間店問有沒有賣」。找不到是 127、找到了但不能執行是 126。HW2 的 SnApper 與 sftp_watchd 規定要在 $PATH 裡，judge 是用 `which` 找它們的，所以放哪、權限給多少都要驗證。
B> **type 名稱**：告訴你它是 alias、builtin、function 還是哪個路徑的檔案；**command -v**（可攜、適合腳本）、**which**（只找 PATH 上的檔）
B> **exit 127**：command not found（PATH 上沒有）；**exit 126**：找到但不能執行（沒 x 權限、或是目錄）
B> `echo "$PATH" | tr ':' '\n'` 一行一個看清楚；自己的工具慣例放 **/usr/local/bin**
B> **sudo 會把 PATH 換成 sudoers 的 secure_path**，所以「自己跑得到、sudo 跑不到」先查這裡
B> 剛搬動過執行檔還是跑到舊路徑：bash 有快取，**hash -r** 清掉
X> type ls cd SnApper
X> command -v sftp_watchd || echo "not in PATH"
X> sudo sh -c 'echo $PATH'
?mc 執行自己的腳本得到 exit status 126，最可能的原因是？
+ 檔案找到了，但沒有執行權限
- PATH 上找不到這個指令
- 腳本裡某個指令回傳失敗
- 腳本被 SIGKILL 終止
E> 127 = not found、126 = 不能執行、137 = 128 + 9（SIGKILL）。
?cmd 用可攜（POSIX）的方式查出 SnApper 會被解析到哪個路徑：
= command -v SnApper
= which SnApper
= type SnApper
E> 腳本中建議 command -v；type 還能看出 alias / builtin。
?mc `mytool` 自己執行正常，但 `sudo mytool` 顯示 command not found。最可能的原因？
+ sudo 使用 sudoers 的 secure_path，其中沒有 mytool 所在的目錄
- sudo 只能執行 ELF 執行檔，不能執行 shell script 或其他腳本
- root 沒有權限讀取一般使用者的家目錄，所以找不到 mytool
- mytool 沒有設定 setuid bit，所以 sudo 拒絕以 root 身分執行它
E> 放到 /usr/local/bin 這類 secure_path 內的目錄就解決。
