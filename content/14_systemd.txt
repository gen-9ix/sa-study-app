@CARD systemd.intro | systemd 是什麼
A> systemd 是系統的「總管家」：開機時是 PID 1，負責把所有服務按照依賴關係排好、一起啟動；還兼管主機名、時間、語系、登入、網路、DNS 等雜事。它用 cgroups 幫每個服務「分房間」，所以永遠知道哪個 process 屬於哪個服務。
B> **system and service manager**：Debian 8 (jessie) 起的預設 init system
B> **Transactional、dependency-based** 的服務控制邏輯：依依賴關係決定要啟動哪些 unit
B> 相容 **SysV / LSB init scripts**，可取代 sysvinit
B> 用 Linux **control groups (cgroups)** 追蹤 process：服務 fork 出的子孫都在同一個 cgroup，不會「跑丟」
B> 另附 logging daemon（journald）與工具：hostname、time/date、locale、user sessions、system accounts、runtime directories、網路設定、名稱解析、網路校時
?mc systemd 用什麼機制追蹤「某個服務產生的所有 process」？
+ Linux control groups（cgroups）
- PID 檔案（/var/run/*.pid）
- 每個 process 的 PPID 父子鏈
- /etc/inittab 中記錄的 runlevel 與 PID
E> 投影片：Keeps track of processes using Linux control groups。process 就算 double fork 脫離父子關係，仍留在同一個 cgroup。
?tf systemd 可以執行傳統的 SysV init script。
=T
E> Supports SysV and LSB init scripts and works as a replacement for sysvinit。
?mc 下列哪一項「不是」投影片列出的 systemd 附帶功能？
+ 編譯 kernel module
- 設定 hostname
- 管理 user sessions
- 網路校時（time synchronization）
E> 列出的有 hostname、time/date、locale、user sessions、system accounts、runtime directories、網路設定、名稱解析、網路校時。

@CARD systemd.cgroup | Control Groups v2
A> cgroup 像公司的「部門樹」：process 是員工，被分到不同部門（cgroup）；資源（CPU、記憶體、I/O、PID 數）是部門預算，沿著樹往下分配。規定只有「最底層的小組」可以放員工，中層部門只管預算。
B> 用**階層**方式組織 process，並沿階層**分配系統資源**：CPU、Memory、I/O、PID
B> systemctl status 的 **CGroup:** 樹：init.scope（PID 1）、**system.slice**（各 .service）、**user.slice**（使用者 session）
B> **.slice**：分組用的中間節點；**.service / .scope**：真正放 process 的葉節點
B> **No internal process rule**：process 只能放在**葉節點** cgroup（啟用 controller 的非 root cgroup 不能同時有 process 和子 cgroup）
B> 查看工具：**systemd-cgls**（樹狀）、**systemd-cgtop**（即時資源用量）
X> $ systemctl status            # 最下面有整棵 CGroup 樹
X> $ cat /proc/self/cgroup
X> 0::/user.slice/user-1000.slice/session-3.scope
?mt 配對 cgroup 單位類型：
> .slice :: 分組用的中間節點，本身不放 process
> .service :: systemd 啟動的服務，放它的 process
> .scope :: 外部建立的一群 process（如使用者登入 session）
> init.scope :: PID 1 所在的位置
E> slice 分層、service/scope 放 process（no internal process rule）。
?mc cgroups v2 的 no internal process rule 指的是？
+ process 只能放在葉節點 cgroup，中間節點只負責分配資源
- 一個 process 不能同時屬於兩個 user 的 cgroup
- root cgroup 底下不能放任何 process
- 每個 cgroup 裡只能放一個 process
E> 所以 systemd 才把 process 放在 .service/.scope，而 .slice 只做分組。
?cmd 即時查看各 cgroup（服務）的 CPU、記憶體用量排行：
= systemd-cgtop
E> 類似 top，但以 cgroup 為單位。
?tf cat /proc/self/cgroup 可以看出目前 shell 屬於哪個 cgroup。
=T
E> cgroup v2 只有一行 0::/路徑。

@CARD systemd.cgfs | cgroups v2 檔案介面
A> cgroup 被做成一個「檔案櫃」：/sys/fs/cgroup 底下每個資料夾就是一個 cgroup，打開檔案就能看成員名單（cgroup.procs）和預算上限（memory.max、cpu.max）。寫檔案就等於改規則。
B> 以**檔案系統**呈現：**/sys/fs/cgroup**，**一個 cgroup 一個目錄**
B> **cgroup.procs**：這個 cgroup 裡的 PID 清單
B> **cgroup.events**：**populated 0/1**（底下是否還有 process）、frozen
B> **cgroup.subtree_control**：開放給子 cgroup 使用的 controller
B> controller 檔案：cpu.max、cpu.weight、memory.current、memory.max、pids.current、pids.max；值 **max** 代表不限制
X> $ cd /sys/fs/cgroup/system.slice/cron.service
X> $ cat cgroup.procs      # 1153
X> $ cat memory.max        # max
?mc 想知道 cron.service 目前有哪些 PID，應讀哪個檔案？
+ /sys/fs/cgroup/system.slice/cron.service/cgroup.procs
- /sys/fs/cgroup/system.slice/cron.service/cgroup.threads.max
- /sys/fs/cgroup/cron/tasks.list（cgroup v1 的格式）
- /etc/systemd/system/cron.service 中的 MainPID=
E> 每個 cgroup 一個目錄，cgroup.procs 列出 PID。
?fill cgroup.events 中顯示底下是否還有 process 的欄位是＿＿
= populated
E> populated 1 表示還有 process，0 表示空了；systemd 用它判斷服務是否已完全結束。
?tf memory.max 的內容是 max，代表該 cgroup 沒有記憶體上限。
=T
E> 值為 max 代表不限制；systemctl edit 設 MemoryMax= 後這裡會變成數字。

@CARD systemd.resource | systemd 資源控制：Weight、Limit、Throttle
A> 三種管法：Weight 是「塞車時才看的優先權」（不忙時大家隨便用）；Hard limit 是「預算上限，超過就處分」（記憶體超過 MemoryMax 直接被 OOM kill）；Throttle 是「接近上限就踩煞車」（超過 MemoryHigh 變慢、回收記憶體，但不會被殺）。
B> **Weight**：只在資源**忙碌、搶用時**才按比例分配；**CPUWeight=、IOWeight=**（預設 **100**）
B> **Hard limit**：**CPUQuota=**（cpu.max）、**MemoryMax=**（memory.max）、**TasksMax=**（pids.max）；超過 MemoryMax → **OOM kill**
B> **Throttle**：超過 **MemoryHigh=**（memory.high）→ **變慢、回收記憶體**，不殺 process
B> 設定方式：**systemctl edit** 寫進 [Service]，或 **systemctl set-property** 直接套用（預設會持久保存）
X> # systemctl edit myapp.service
X> [Service]
X> CPUWeight=200     # cpu.weight
X> CPUQuota=50%      # cpu.max
X> MemoryHigh=800M   # memory.high
X> MemoryMax=1G      # memory.max
X> TasksMax=512      # pids.max
X> $ systemctl set-property myapp.service MemoryMax=500M
?mt 配對 systemd 設定與 cgroup 檔案：
> CPUWeight= :: cpu.weight
> CPUQuota= :: cpu.max
> MemoryMax= :: memory.max
> MemoryHigh= :: memory.high
> TasksMax= :: pids.max
E> 投影片右邊的註解就是對照表。
?mc 服務的記憶體用量超過 MemoryHigh= 但還沒到 MemoryMax=，會發生什麼事？
+ 被 throttle：變慢並回收記憶體，但不會被殺
- 服務會被 systemd 停止，等記憶體降下來再重啟
- 服務會被 systemd 自動重新啟動
- 沒有任何影響，只是記錄一筆 log
E> MemoryHigh 是軟性煞車；MemoryMax 才是硬上限，超過會 OOM kill。
?mc 兩個服務 CPUWeight 分別是 200 與 100。系統 CPU 很閒時，哪個說法正確？
+ 都能盡量用 CPU；weight 只在搶 CPU 時才有作用
- 第一個服務永遠固定拿到 2/3 的 CPU 時間，不管系統忙不忙
- 第二個服務最多只能使用 50% 的 CPU，即使系統很閒
- weight 會依比例換算成固定的 CPUQuota 上限
E> Share only when resource is busy。想要硬上限要用 CPUQuota=。
?cmd 不開編輯器，直接把 myapp.service 的記憶體硬上限設為 500M：
= systemctl set-property myapp.service MemoryMax=500M
= systemctl set-property myapp MemoryMax=500M
E> 加 --runtime 則只在這次開機有效。
?sa 某 Web 服務偶爾記憶體暴衝把整台機器拖垮。請說明如何用 systemd 限制它，並比較 MemoryHigh= 與 MemoryMax= 的差異，以及何時該用 CPUWeight= 而不是 CPUQuota=。
R> 用 systemctl edit web.service 在 [Service] 加入 MemoryHigh=（例如 800M）與 MemoryMax=（例如 1G），或用 systemctl set-property 直接設定；systemd 會寫入該服務 cgroup 的 memory.high / memory.max。
R> MemoryHigh 是 throttle：超過時 kernel 讓 process 變慢並積極回收記憶體，但不會殺掉它；MemoryMax 是硬上限，超過時會觸發 OOM killer 殺掉該 cgroup 內的 process（可搭配 Restart= 讓服務自動重啟）。通常 High 設得比 Max 低一些，先煞車再處分。
R> CPUWeight 是相對權重，只在 CPU 忙碌、多個服務搶用時才按比例分配，閒時不設限，適合「重要服務優先」；CPUQuota 是絕對上限（如 50% = 每週期最多半顆 CPU），即使 CPU 很閒也不能超過，適合防止單一服務吃滿。
P> 用 systemctl edit / set-property 設定 MemoryHigh、MemoryMax
P> MemoryHigh 超過會 throttle、不會被殺
P> MemoryMax 超過會 OOM kill
P> CPUWeight 只在搶資源時生效；CPUQuota 是硬上限

@CARD systemd.systemctl | systemctl 指令總覽
A> systemctl 是跟總管家溝通的遙控器：start/stop 是「現在開/關」，enable/disable 是「開機時要不要自動開」，mask 是「把插頭拔掉並封住插座」，連別人想幫你開都開不了。
B> **status [unit]**：狀態、最近 log、cgroup；**cat unit**：印出 unit 檔與所有 drop-in
B> **start / stop**：立即啟動 / 停止（不影響開機行為）
B> **enable / disable**：依 [Install] 建立 / 移除 symlink（影響開機）；**enable --now** = enable + start
B> **kill**：送訊號給服務的 process（預設 SIGTERM，可用 -s 指定）
B> **mask / unmask**：把 unit 連到 **/dev/null**，讓它**完全無法被啟動**（手動或被依賴都不行）
B> **list-unit-files**、**list-dependencies**；改完 unit 檔後 **daemon-reload**
?mt 配對 systemctl 子指令：
> enable :: 建立 symlink，開機時自動啟動
> start :: 現在立刻啟動，不影響開機設定
> mask :: 連到 /dev/null，任何方式都無法啟動
> daemon-reload :: 修改 unit 檔後重新載入設定
> cat :: 顯示 unit 檔內容與 drop-in
E> enable 和 start 是兩件事，所以常用 enable --now。
?mc 某服務 disable 之後，仍然因為別的服務 Wants= 它而被啟動。要徹底阻止它被啟動，應該用？
+ systemctl mask
- systemctl stop
- systemctl kill
- systemctl daemon-reload
E> disable 只移除 [Install] 建立的 symlink，被依賴時仍會啟動；mask 把它指向 /dev/null。
?cmd 修改了 /etc/systemd/system/myapp.service 之後，讓 systemd 重新讀取 unit 檔：
= systemctl daemon-reload
E> 不 reload 的話 systemctl 會警告 unit file changed on disk。
?cmd 讓 nginx 開機自動啟動，並且現在就啟動（一個指令）：
= systemctl enable --now nginx
= systemctl enable --now nginx.service
= systemctl --now enable nginx
E> --now 會同時 start（disable --now 則同時 stop）。
?cmd 顯示 sshd.service 的 unit 檔內容（含所有 drop-in）：
= systemctl cat sshd
= systemctl cat sshd.service
E> 比直接 cat 檔案好：會告訴你實際生效的是哪些檔案。

@CARD systemd.unitfile | Unit 檔結構：[Unit]、[Service]、[Install]
A> 一份 unit 檔像「員工資料卡」：[Unit] 是基本資料與人際關係（我是誰、在誰之後上班、需要誰）；[Service] 是工作內容（怎麼啟動、掛了怎麼辦）；[Install] 是「被誰錄取」（enable 時掛到哪個 target 底下）。
B> **[Unit]**：通用資訊：Description=、Documentation=、依賴（Wants=、Requires=）、順序（After=、Before=）
B> **[Service]**：服務專屬設定：Type=、ExecStart=、Restart=…；也可用 **systemd.exec(5)** 的選項（User=、Environment=…）
B> **[Install]**：安裝資訊，**只給 enable / disable 用**：WantedBy=、RequiredBy=
B> 沒有 [Install] 的 unit 不能 enable（通常是被別人依賴或由 timer / socket 觸發）
X> [Unit]
X> Description=OpenSSH Daemon
X> After=network.target sshdgenkeys.service
X> Wants=sshdgenkeys.service ssh-access.target
X> [Service]
X> Type=notify-reload
X> ExecStart=/usr/bin/sshd -D
X> KillMode=process
X> Restart=always
X> [Install]
X> WantedBy=multi-user.target
?mt 配對設定與所在區段：
> Description= :: [Unit]
> After= :: [Unit]
> ExecStart= :: [Service]
> Restart= :: [Service]
> WantedBy= :: [Install]
E> [Install] 只有 enable/disable 會讀。
?mc [Install] 區段的用途是？
+ 給 enable / disable 用的資訊
- 告訴 apt 如何安裝這個套件
- 告訴 apt 或 dnf 如何安裝這個套件的資訊
- 宣告這個服務要在哪些服務之後啟動
E> 提供 systemctl enable / disable 安裝 unit 時需要的資訊。Installation information for the unit, used by enable / disable。
?tf systemd.exec(5) 的選項（例如 User=、Environment=）可以寫在 [Service] 區段。
=T
E> [Service] includes options in systemd.exec。

@CARD systemd.dropin | Drop-in 片段與 systemctl edit
A> 不要直接改「出廠說明書」（/usr/lib 底下的 unit，套件更新會被蓋掉）。改用「便利貼」：systemctl edit 在 /etc/systemd/system/xxx.service.d/override.conf 貼一張，只寫要改的那幾行，其餘沿用原本設定。
B> **systemctl edit [unit]**：建立或編輯 drop-in：**/etc/systemd/system/<unit>.d/override.conf**
B> **--full**：改為編輯整份 unit（複製到 /etc/systemd/system/<unit>）
B> 編輯器中只有兩行註解之間的內容會被存檔；下方會顯示原 unit 內容供參考
B> 用預設編輯器（$SYSTEMD_EDITOR / $EDITOR）；存檔後自動 daemon-reload
B> 清掉清單型設定要先寫空值：例如改 ExecStart 要先 **ExecStart=** 再寫新的 ExecStart=
X> # systemctl edit sshd.service
X> [Service]
X> ExecStart=
X> ExecStart=/usr/bin/sshd -D -o LogLevel=VERBOSE
?mc 為什麼建議用 drop-in 而不是直接修改 /usr/lib/systemd/system/sshd.service？
+ /usr/lib 的檔案屬於套件、更新會被覆蓋；drop-in 放 /etc 只覆寫需要的部分
- drop-in 會被 systemd 預先編譯成二進位，執行速度比完整的 unit 檔快很多
- /usr/lib 底下的檔案是唯讀掛載的，連 root 也無法修改，只能改 /etc 的版本
- systemd 不會讀取 /usr/lib 底下的 unit，只會讀 /etc 的設定
E> /etc 的設定優先，且不會被 apt 蓋掉。
?fill systemctl edit nginx.service 建立的 drop-in 檔路徑是 /etc/systemd/system/nginx.service.d/＿＿
= override.conf
E> 也可以手動在 .d/ 目錄放任意 *.conf。
?cmd 用編輯器修改 myapp.service 的「完整」unit 檔（不是 drop-in）：
= systemctl edit --full myapp.service
= systemctl edit --full myapp
= systemctl edit myapp.service --full
E> 會在 /etc/systemd/system/ 產生完整副本。
?tf 在 drop-in 想換掉原本的 ExecStart=，直接寫一行新的 ExecStart= 就好，不需要其他處理。
=F
E> 對一般服務，ExecStart= 可累加，必須先寫空的 ExecStart= 清除舊值，否則會報錯（非 oneshot 只能有一個）。

@CARD systemd.path | Unit 搜尋路徑與優先順序
A> systemd 找 unit 就像找文件：先看「你自己桌上」（/etc，管理員設定），再看「部門共用櫃」（/usr/local/lib，本機自裝），最後才看「公司出廠檔案」（/usr/lib，套件提供）。同名時越前面越優先。
B> System unit：**/etc/systemd/system/** → **/usr/local/lib/systemd/system/** → **/usr/lib/systemd/system/**（前者優先）
B> /etc：管理員的設定與 enable 產生的 symlink；/usr/lib：套件安裝的 unit
B> User unit（systemctl --user）：$XDG_CONFIG_DIRS/systemd/user、/etc/systemd/user、$XDG_DATA_HOME/systemd/user（~/.local/share/systemd/user）、/usr/local/lib/systemd/user、/usr/lib/systemd/user
B> 查詢實際使用的檔案：**systemctl cat**、systemctl show -p FragmentPath
?ord 依優先順序（高 → 低）排列 system unit 搜尋路徑：
> /etc/systemd/system/
> /usr/local/lib/systemd/system/
> /usr/lib/systemd/system/
E> /etc 最優先，所以管理員的設定可以蓋過套件預設。
?mc 自己寫的 myapp.service 應該放在哪裡最合適？
+ /etc/systemd/system/myapp.service
- /usr/lib/systemd/system/myapp.service
- /var/lib/systemd/myapp.service
- /run/myapp.service
E> /usr/lib 留給套件管理；管理員自訂放 /etc。
?tf 使用者層級的 unit 可以放在 ~/.local/share/systemd/user/ 底下，用 systemctl --user 管理。
=T
E> 對應 $XDG_DATA_HOME/systemd/user。

@CARD systemd.deps | 依賴：Requires、Wants、BindsTo、Upholds
A> 四種「需要你」的強度：Wants 是「希望你來，不來我也照常上班」；Requires 是「你沒來我就算失敗」；BindsTo 是「你一走我也走」；Upholds 是「你倒了我就把你拉起來」。
B> **Requires=**：列出依賴，**平行啟動**；依賴失敗 → 這個 unit 被標記為 **failed**
B> **Wants=**：較寬鬆；依賴失敗**不會**讓這個 unit failed → **大多數情況建議用 Wants**
B> **BindsTo=**：比 Requires 更嚴格；依賴**掛掉時這個 unit 也會停止**
B> **Upholds=**：比 BindsTo 更積極；依賴掛掉時會**把依賴重新啟動**
B> 依賴 ≠ 順序：只寫 Requires 沒寫 After 時兩者是**同時**啟動的
?mt 配對依賴關係：
> Wants= :: 依賴失敗也不影響自己（建議預設使用）
> Requires= :: 依賴失敗，自己被標記為 failed
> BindsTo= :: 依賴停止或崩潰，自己也跟著停止
> Upholds= :: 依賴崩潰時，自動把依賴重新啟動
E> 強度：Wants < Requires < BindsTo；Upholds 更積極地維持依賴存活。
?mc A.service 寫了 Requires=B.service，但沒有 After=B.service。A 和 B 的啟動順序是？
+ 同時（平行）啟動
- 先 B 再 A
- 先 A 再 B
- 只啟動 A
E> All the dependencies will be executed in parallel；要排順序需要另外寫 After=。
?mc 為什麼投影片建議大多數情況用 Wants= 而不是 Requires=？
+ 依賴失敗時不會連帶讓自己 failed，系統比較有韌性
- Wants= 的依賴會平行啟動，所以比較快
- Requires= 已經被新版 systemd 淘汰
- Wants= 會自動加上對應的 After=
E> Wants 是 less restrictive 的版本。
?tf 若 A 有 BindsTo=B，當 B 崩潰時，A 也會被停止。
=T
E> BindsTo 比 Requires 更嚴格：依賴停止或崩潰，自己也一起停。

@CARD systemd.order | 順序：Before= / After= 不是依賴
A> After= 只是「排隊順序」，不是「邀請函」：寫了 After=network.target 不代表會把網路叫起來，只代表如果它也要啟動，就排在它後面。要「叫起來」得用 Wants/Requires，兩者通常搭配使用。
B> **Before=**：這個 unit 要在列出的 unit **之前**啟動
B> **After=**：這個 unit 要在列出的 unit **之後**啟動
B> **它們不是依賴**：只指定啟動順序；要拉起依賴請用 Requires= / Wants= / BindsTo=
B> 常見組合：**Wants=network-online.target + After=network-online.target**（真的等網路可用）
B> 關機時順序**反過來**（先啟動的後停止）
?mc myapp.service 只寫了 After=postgresql.service，沒有任何 Wants/Requires。啟動 myapp 時會？
+ 不會自動啟動 postgresql；若 postgresql 剛好也要啟動，myapp 會排在它之後
- systemd 會自動先啟動 postgresql，等它 active 之後再啟動 myapp
- 因為只寫 After= 而沒有寫 Requires=，myapp 會因缺少依賴啟動失敗
- myapp 會一直卡在 activating，直到有人手動啟動 postgresql 為止
E> These are not dependencies, only startup order is specified。
?tf After= 和 Before= 會讓 systemd 自動啟動列出的 unit。
=F
E> 只控制順序，要搭配 Wants=/Requires=。
?mc HAProxy 的 unit 同時寫了 Wants=network-online.target 與 After=network-online.target，目的是？
+ 拉起 network-online.target，並等網路可用後才啟動 HAProxy
- 網路斷線時，systemd 會自動停止 HAProxy，等網路恢復之後再重新把它啟動
- 網路斷線時，systemd 會自動停止 HAProxy，等網路恢復再啟動
- 只是重複的寫法，Wants= 已經包含順序，再寫 After= 沒有額外效果
E> Wants 負責拉起、After 負責排序，兩者缺一不可。

@CARD systemd.defdeps | 預設依賴：DefaultDependencies
A> 每個服務都會被自動加上「入職手續」：要等系統初始化（sysinit、basic）完成才上班，而且一宣布關機（shutdown.target）就收工。只有很早期開機要用的服務才會關掉這個預設。
B> 除非設定 **DefaultDependencies=no**，service 會自動加上：
B> **Requires=sysinit.target**
B> **After=sysinit.target basic.target**
B> **Conflicts=shutdown.target**、**Before=shutdown.target**
B> Conflicts=：兩者不能同時存在 → 關機（啟動 shutdown.target）時會停止這個服務
?mc 為什麼一般服務在關機時會被停止？
+ 預設依賴有 Conflicts=shutdown.target，關機啟動它時就會停掉服務
- 因為 kernel 在關機時會直接對所有 process 送 SIGKILL 強制結束
- 因為每個服務都必須寫 ExecStop=，systemd 關機時會依照寫入順序逐一執行它們
- 因為 multi-user.target 在關機時會被刪除，底下所有 WantedBy 它的服務也就跟著消失
E> 再加上 Before=shutdown.target，保證服務在 shutdown.target 之前停好。
?mt 配對預設依賴：
> Requires= :: sysinit.target
> After= :: sysinit.target basic.target
> Conflicts= :: shutdown.target
> Before= :: shutdown.target
E> 投影片 Systemd default dependencies。
?fill 不想要自動加上預設依賴時，在 [Unit] 寫 DefaultDependencies=＿＿
= no
= false
= 0
E> 只有開機極早期或關機流程中的特殊 unit 才需要關掉預設依賴。

@CARD systemd.install | enable 的原理：.wants/ symlink
A> enable 不會「啟動」任何東西，它只是在 target 的「邀請名單資料夾」（xxx.target.wants/）放一張指向你的 symlink 名片。開機時 target 啟動，就會照名單把你叫起來。
B> 用 **systemctl enable / disable** 安裝與解除安裝 unit

B> disable 移除這些 symlink；**unit 檔本身不會被刪**
X> $ sudo systemctl enable sshd.service
X> Created symlink '/etc/systemd/system/multi-user.target.wants/sshd.service'
X>   → '/usr/lib/systemd/system/sshd.service'.
?mc systemctl enable sshd.service 實際做了什麼？
+ 在 multi-user.target.wants/ 建立指向 unit 檔的 symlink
- 立刻啟動 sshd，並把目前狀態記錄在 /var/lib/systemd，下次開機時恢復成同樣的狀態
- 把 unit 檔從 /usr/lib/systemd/system 複製一份到 /etc/systemd/system/
- 在 /etc/rc.local 加入一行 systemctl start sshd.service，讓每次開機時都會執行它
E> 依 WantedBy=multi-user.target 建立 symlink；不會立即啟動。
?fill 某服務 [Install] 寫 WantedBy=multi-user.target，enable 後 symlink 會放在 /etc/systemd/system/＿＿/ 目錄中
= multi-user.target.wants
E> RequiredBy= 會放在 <target>.requires/。
?tf systemctl disable 會刪除 unit 檔。
=F
E> 只移除 symlink。

@CARD systemd.target | Target 與 SysV runlevel
A> Target 是「套餐」：multi-user.target 是「多人文字模式套餐」，graphical.target 是「再加上圖形介面」。開機時 systemd 點 default.target 這份套餐（其實是指向某個套餐的別名），套餐裡的每道菜（unit）就會被端上來。
B> 工作以 unit 組織；**target 是一群 unit 的集合**，用來把系統組到某個狀態
B> target 可以建立在其他 target 之上（graphical → multi-user → basic …）
B> 開機時啟動 **default.target**（通常是 graphical 或 multi-user 的別名）：**systemctl get-default / set-default**
B> runlevel 對照：**0 poweroff**、**1 rescue**（單人模式）、**2/3/4 multi-user**、**5 graphical**、**6 reboot**；另有 **emergency.target**、**network-online.target**
B> 切換到某 target 並停掉不屬於它的 unit：**systemctl isolate**
?mt 配對 SysV runlevel 與 systemd target：
> 0 :: poweroff.target
> 1 :: rescue.target
> 3 :: multi-user.target
> 5 :: graphical.target
> 6 :: reboot.target
E> 2、3、4 都對應 multi-user.target。
?cmd 查詢系統預設開機的 target：
= systemctl get-default
E> default.target 是指向實際 target 的 symlink。
?cmd 把預設開機 target 改成純文字的多使用者模式：
= systemctl set-default multi-user.target
= systemctl set-default multi-user
E> set-default 會改 default.target 這個 symlink 指向的 target。
?mc emergency.target 與 rescue.target 的差別？
+ emergency 啟動的東西比 rescue 更少
- 兩者完全相同
- rescue 比 emergency 啟動更少服務
- emergency 會啟動網路，rescue 不會
E> emergency 只給一個 root shell，幾乎不啟動任何服務、root 可能唯讀；rescue 會掛載本機檔案系統並啟動基本系統。emergency 是最精簡的救援環境。

@CARD systemd.type | Service Type：什麼時候算「啟動完成」
A> Type 決定 systemd 何時把服務標成「已啟動」，好讓排在後面的服務出發：simple 是「人一出門就算」；exec 是「確定上車了才算」；notify 是「到了公司打電話回報 READY 才算」；oneshot 是「事情做完回家才算」。
B> **simple**：主 process **fork() 之後立刻**視為 started（就算 exec 失敗也已經算啟動）
B> **exec**：類似 simple，但等到**執行檔真的被 exec 成功**才算 started
B> **notify / notify-reload**：等服務透過 **sd_notify(3)** 送出 **READY=1** 才算 started；notify-reload 另外支援送 **SIGHUP** 來 reload
B> **oneshot**：**主 process 結束之後**才算完成；常搭配 **RemainAfterExit=yes**（結束後仍顯示 active）
B> 其他：forking（傳統 daemon 自己 fork 到背景）
?mt 配對 Type= 與「started」的時機：
> simple :: fork() 之後立刻
> exec :: 執行檔被 exec 成功之後
> notify :: 服務送出 READY=1 之後
> oneshot :: 主 process 結束之後
E> 投影片 Systemd service type。
?mc 一個只需執行一次的初始化腳本（跑完就結束），Type 最適合設為？
+ oneshot
- simple
- notify
- exec
E> oneshot 要等程式結束才算完成，排在它後面的 unit 才會開始。
?mc 用 Type=simple 時，若 ExecStart= 的執行檔路徑打錯，systemctl start 會？
+ 先回報成功，之後才 failed
- 立刻回報失敗
- 卡住直到逾時
- 自動改用 Type=exec
E> 仍回報成功（fork 後就算 started），之後服務才變成 failed。這正是 exec 比 simple 好的地方：exec 失敗時 start 會直接回報錯誤。
?tf Type=notify 的服務必須主動送 READY=1，systemd 才會認為它啟動完成。
=T
E> 透過 sd_notify(3)；sshd 用的是 notify-reload。

@CARD systemd.restart | Restart= 重啟策略
A> Restart= 是「服務掛掉時要不要自動扶起來」的規則。always 是無條件扶；on-failure 是「不正常結束才扶」（最常用）；on-abnormal 不管 exit code 只看是不是被訊號殺、逾時、OOM；on-abort 只在被訊號打死時扶。
B> **no**：都不重啟（預設）
B> **always**：任何結束都重啟（包含正常 exit 0）
B> **on-success**：只有 **clean exit**（exit code 0 或 SuccessExitStatus）才重啟
B> **on-failure**：**非 0 exit code、被訊號殺、逾時、OOM** 都重啟（clean exit 不重啟）
B> **on-abnormal**：**被訊號殺、逾時、OOM**（exit code 非 0 不算）
B> **on-abort**：**只有被未捕捉的訊號殺掉**
B> 相關：RestartSec=（重啟前等多久）、StartLimitBurst= / StartLimitIntervalSec=（短時間重啟太多次就放棄）
?mc 服務以 exit 1 結束。下列哪個 Restart= 設定「不會」重啟它？
+ on-abnormal
- always
- on-failure
- 以上全部都會重啟
E> on-abnormal 只管 unclean signal、timeout、OOM；unclean exit code 不算。
?mc 服務被 OOM killer 殺掉，下列哪個設定不會重啟它？
+ on-abort
- on-failure
- on-abnormal
- always
E> 表格中 OOM 這一列：always、on-failure、on-abnormal 是 ✅，on-abort 與 on-success 是 ❌。
?mt 配對 Restart= 值：
> always :: 任何情況都重啟
> on-success :: 只有正常結束才重啟
> on-failure :: 非 0 exit、被訊號殺、逾時、OOM 都重啟
> on-abort :: 只有被訊號殺才重啟
E> 投影片 Systemd service restart policy 表格。
?fill 一般長駐服務最常用、但正常 exit 0 時不會被重啟的設定是 Restart=＿＿
= on-failure
E> on-failure 涵蓋非 0 exit、被訊號殺、逾時與 OOM，正常結束則不重啟。
?sa 請說明 systemd 的 Restart=on-failure、on-abnormal 與 on-abort 三者在下列四種情況下是否會重啟服務：(1) exit code 0 (2) exit code 1 (3) 被 SIGSEGV 殺掉 (4) 啟動逾時。
R> on-failure：(1) 不重啟 (2) 重啟 (3) 重啟 (4) 重啟。
R> on-abnormal：(1) 不重啟 (2) 不重啟 (3) 重啟 (4) 重啟。
R> on-abort：(1) 不重啟 (2) 不重啟 (3) 重啟（被未捕捉的訊號殺掉）(4) 不重啟。
R> 規律：on-failure 涵蓋所有非正常結束；on-abnormal 不管 exit code，只看訊號、逾時、OOM、watchdog；on-abort 只看訊號。
P> on-failure：exit 1、訊號、逾時都重啟，exit 0 不重啟
P> on-abnormal：只有訊號、逾時重啟
P> on-abort：只有被訊號殺才重啟

@CARD systemd.exec | Exec*= 與逾時
A> 服務的「上下班流程」：ExecStartPre 是上班前打卡準備，ExecStart 是主要工作，ExecStartPost 是開工後的收尾，ExecReload 是「重新讀設定」，ExecStop 是下班。前面加「-」代表「這步失敗沒關係，繼續走」。
B> **ExecStart=**：啟動服務時執行的指令（主 process）
B> **ExecStartPre= / ExecStartPost=**：在 ExecStart 之前 / 之後額外執行；前綴 **「-」** 代表**允許失敗、不影響後續**
B> **ExecReload=**：觸發重新載入設定（systemctl reload）
B> **ExecStop=**：停止服務的指令（沒寫就直接送 KillSignal=，預設 SIGTERM）
B> **TimeoutSec= / TimeoutStartSec= / TimeoutStopSec=**：等待啟動 / 停止的時間
B> 指令要用**絕對路徑**（或在 PATH 中）；不經過 shell，要用管線或 && 得寫 /bin/sh -c '…'
X> ExecStartPre=-/usr/lib/apt/apt-helper wait-online
X> ExecStart=/usr/lib/apt/apt.systemd.daily update
X> ExecReload=/bin/kill -HUP $MAINPID
?mc ExecStartPre=-/usr/bin/foo 中的「-」代表？
+ 這個指令失敗也不影響服務繼續啟動
- 以非 root 身分執行
- 在背景執行，不等它跑完就繼續
- 只在第一次啟動時執行
E> Can be prefixed with a “-”, allowing this command to fail and not affect the rest。
?mt 配對 Exec 設定：
> ExecStart= :: 主要的啟動指令
> ExecStartPre= :: 主指令之前的準備工作
> ExecReload= :: systemctl reload 時執行
> ExecStop= :: 停止服務時執行
> TimeoutStopSec= :: 停止時最多等多久
E> ExecStartPre/Post 可加「-」允許失敗；沒寫 ExecStop 時預設送 SIGTERM。
?tf ExecStart=echo hi > /tmp/log 會由 shell 處理重導向，把 hi 寫進 /tmp/log。
=F
E> ExecStart 不經過 shell，> 會被當成普通參數；要寫 /bin/sh -c 'echo hi > /tmp/log'。

@CARD systemd.envio | Environment 與標準輸入輸出

@CARD systemd.examples | 讀懂真實 unit：sshd、haproxy、apt-daily

- 讓 sshd 同一時間只能有一個 process，避免多個 SSH 連線之間互相干擾衝突
- 讓 sshd 被 kill 時自動重啟，不需要另外設定 Restart=
- 讓每個 SSH 連線都成為獨立的 service unit，方便個別停止
E> 預設 KillMode=control-group 會殺掉整個 cgroup，包括你的登入 session。

= 143

@CARD systemd.p_kill | 實作：停止服務時發生什麼事（KillMode）
A> systemctl stop 的流程像「下班廣播」：先執行 ExecStop（如果有），再對 process 送 KillSignal（預設 SIGTERM）請它收拾；等 TimeoutStopSec（預設 90 秒）還沒走，就送 SIGKILL 強制清場。KillMode 決定廣播給「誰」。
B> 停止流程：**ExecStop=** → 送 **KillSignal=**（預設 **SIGTERM**）→ 等 **TimeoutStopSec=**（預設 90s）→ 仍在就送 **SIGKILL**（SendSIGKILL=yes）
B> **KillMode=control-group**（預設）：cgroup 裡**所有** process 都收到訊號
B> **KillMode=mixed**：SIGTERM 只給主 process，最後的 SIGKILL 給整個 cgroup
B> **KillMode=process**：只殺主 process（sshd 用它保留既有連線）；**none**：不建議
B> 手動送訊號：**systemctl kill -s HUP x**（也可 --kill-whom=main）
X> systemctl kill -s SIGHUP nginx
X> systemctl show nginx -p KillMode,KillSignal,TimeoutStopUSec
?ord 預設情況下 systemctl stop 的順序：
> 執行 ExecStop=（若有設定）
> 對 cgroup 內 process 送 SIGTERM
> 等待 TimeoutStopSec
> 仍未結束則送 SIGKILL
E> 這也是 trap TERM 能做清理的原因：先收到的是 SIGTERM。
?mt 配對 KillMode：
> control-group :: 預設，cgroup 內所有 process 都收到訊號
> mixed :: SIGTERM 給主 process，SIGKILL 給全部
> process :: 只對主 process 送訊號
E> none 不會殺任何 process，留下的 process 容易失控，不建議使用。
?cmd 對 nginx.service 的 process 送 SIGHUP（讓它重新讀設定）：
= systemctl kill -s HUP nginx
= systemctl kill -s SIGHUP nginx
= systemctl kill --signal=HUP nginx
= systemctl kill --signal=SIGHUP nginx
= systemctl kill -s HUP nginx.service
E> 一般重新讀設定用 systemctl reload 更好（會執行 ExecReload）。

@CARD systemd.p_foreground | 實作：daemon 要跑在前景（-D、-f、-n）
A> 傳統 daemon 會「自己 fork 到背景再讓爸爸離開」，systemd 要猜哪個才是主 process，很麻煩。現代作法是叫 daemon「別躲到背景」（前景模式），讓 systemd 直接當它的爸爸，最乾淨。投影片 cgroup 樹裡的 sshd -D、cron -f、rsyslogd -n 都是前景模式。
B> 前景旗標：**sshd -D**、**cron -f**、**rsyslogd -n**、nginx 的 daemon off;、dbus-daemon --nofork
B> 前景執行 + **Type=simple / exec / notify**：主 process 就是 ExecStart 啟動的那一個，最好管理
B> 傳統背景 daemon：**Type=forking** + **PIDFile=**（systemd 讀 PID 檔判斷主 process）
B> 自己寫的服務（例如 sftp_watchd）**不要自己 daemonize**（不要 &、nohup、setsid），直接在前景跑，輸出到 stdout/stderr 就會進 journal
B> 輸出被 buffer：Python 用 **python3 -u** 或 PYTHONUNBUFFERED=1，否則 journalctl 可能很久才看到 log
?mc 自己寫的 bash daemon 在腳本最後用 while 迴圈 & 丟到背景，搭配 Type=simple。會發生什麼？
+ 腳本的主 process 立刻結束，systemd 認為服務已停止並清掉整個 cgroup（迴圈也被殺）
- 一切正常，因為 Type=simple 只要求 ExecStart 有被執行過就好
- systemd 偵測到 process 進入背景，會自動把服務改成 Type=forking
- 背景迴圈會被 PID 1 收養成為它的子行程，繼續在 cgroup 之外執行，不受 systemd 管理
E> 在 systemd 底下不要自己 daemonize，直接前景執行。
?mc Python 寫的服務用 print() 輸出 log，但 journalctl -u 很久都看不到。最可能的原因？
+ stdout 被 Python 緩衝了
- journald 只收 stderr
- 要先 systemctl enable 才有 log
- print 不會寫到 stdout
E> stdout 不是 tty 時 Python 會 buffer 輸出，要用 python3 -u、flush=True 或 PYTHONUNBUFFERED=1。同理，C 程式可能要 setvbuf 或 fflush。
?mt 配對前景執行的旗標：
> sshd :: -D
> cron :: -f
> rsyslogd :: -n
E> 投影片 CGroup 樹中可以看到這些參數。

+ AccuracySec 預設 1 分鐘，systemd 會在容許範圍內合併喚醒
- 系統時間錯誤，timedatectl 還沒同步到 NTP
- service 啟動很慢，花了 42 秒才寫出第一行 log
- RandomizedDelaySec 預設是 1 分鐘，所以延後了 42 秒
E> 需要精準到秒就設 AccuracySec=1s。
