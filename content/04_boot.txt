@CARD boot.stages | 開機流程五階段
A> 開機像接力賽：Firmware（裁判鳴槍、檢查場地、挑選跑道）→ Boot loader（第一棒，把 kernel 和 initramfs 搬上場）→ Kernel（第二棒，初始化驅動與記憶體、準備 root filesystem）→ PID 1 systemd（第三棒，啟動並看顧所有服務）→ Login services（終點，讓你登入）。
B> **Firmware**：初始化平台，選擇開機裝置或 EFI 程式
B> **Boot loader**：載入 kernel、modules、（選用）initramfs
B> **Kernel**：初始化驅動與記憶體，準備 root filesystem
B> **PID 1**：啟動 user space，監管服務
B> **Login services**：console、SSH、圖形登入
B> 兩個不同層：boot loader **載入 OS**；service manager **啟動與管理 user-space 服務**
M> 「韌 → 載 → 核 → 一 → 登」：韌體、載入器、核心、PID 1、登入
?ord 依序排列 Linux 開機階段：
> Firmware（BIOS / UEFI）
> Boot loader（GRUB）
> Kernel（含 initramfs）
> PID 1（systemd）
> Login services（getty / sshd / display manager）
E> 每一層都有不同的設定與排錯方法。
?mt 配對階段與職責：
> Firmware :: 初始化平台、選擇開機裝置或 EFI 程式
> Boot loader :: 載入 kernel 與 initramfs
> Kernel :: 初始化驅動、準備 root filesystem
> PID 1 :: 啟動並監管 user-space 服務
E> 先判斷問題卡在哪一層。

@CARD boot.biosuefi | BIOS/MBR vs UEFI/GPT
A> BIOS 像「只會看第一頁的老管理員」：直接執行磁碟 sector 0 的開機碼；UEFI 像「會看目錄的新管理員」：到一個 FAT 格式的資料夾（ESP）裡找指定的 .efi 程式來執行。
B> **Legacy BIOS/MBR**：第一個執行的是**磁碟 sector 0 的開機碼**；分割資訊在 MBR partition table；Debian 例：GRUB boot.img、core.img
B> **UEFI/GPT**：firmware 直接選擇**EFI 程式**；分割資訊在 GPT header 與 partition entries；loader 放在 **EFI System Partition (ESP)**，通常 **FAT**；Debian 例：ESP 上的 shim / GRUB EFI loader
B> Firmware 模式與分割格式是**獨立的選擇**：BIOS 搭配適當開機碼也能從 GPT 開機
B> 判斷：test -d /sys/firmware/efi && echo UEFI
?mc UEFI 開機時，firmware 從哪裡找 boot loader？
+ EFI System Partition（ESP，通常 FAT 格式）中的 .efi 檔
- 磁碟第 0 個 sector 前 446 bytes 的開機碼（boot code）
- /boot/grub/grub.cfg，firmware 直接讀取 GRUB 的選單設定
- /etc/default/grub 中 GRUB_DEFAULT 指定的開機項目
E> BIOS 才是執行 sector 0 的開機碼。
?cmd 判斷目前系統是否以 UEFI 模式開機（存在則印 UEFI）：
= test -d /sys/firmware/efi && echo UEFI
= [ -d /sys/firmware/efi ] && echo UEFI
E> UEFI 開機時 kernel 會提供 /sys/firmware/efi。
?tf BIOS 模式只能從 MBR 分割的磁碟開機，不可能用 GPT。
=F
E> 兩者是獨立選擇；BIOS + GPT 需要 BIOS Boot Partition 放 GRUB core.img。

@CARD boot.mbr | Master Boot Record 結構
A> MBR 是磁碟第一個 512 bytes 的「小紙條」：446 bytes 寫開機咒語、64 bytes 寫四個房間的位置（4 個 partition entry × 16 bytes）、最後 2 bytes 蓋章 55 AA 證明是真的。
B> 經典 MBR：**446 bytes** 開機碼 + **64 bytes** 四個 partition entries + **2 bytes** signature = 512 bytes
B> Signature 在 offset **510、511**，值為 **55 aa**
B> GRUB BIOS 開機碼把控制權交給 **core.img**；EFI loader 走不同路徑
B> GPT 通常保留一個 **protective MBR**；有 MBR signature **不代表**是 BIOS 開機
B> 實際判斷用 lsblk 與分割 metadata
?fill MBR 中 boot code 佔＿＿bytes
= 446
E> 446 + 64 + 2 = 512。
?fill MBR 的 signature 位於 offset 510、511，值為 55 ＿＿（十六進位）
= aa
= AA
E> 55 AA。
?mc MBR 最多可以直接記錄幾個 partition entry？
+ 4
- 8
- 16
- 128
E> 64 bytes ÷ 16 bytes = 4 個 primary partition；GPT 預設可到 128 個。

@CARD boot.grubbios | GRUB 2 的 BIOS 開機路徑
A> BIOS 只會讀很小的一段（boot.img），它的唯一工作就是「去叫 core.img」；core.img 比較大，會載入模組、找到 GRUB 設定，最後顯示選單、載入 kernel + initramfs。
B> BIOS → 讀取磁碟的初始開機碼
B> **boot.img** → 把控制權交給 core.img
B> **core.img** → 載入 modules、找到 GRUB 設定
B> **GRUB menu** → 選 kernel，載入 kernel + initramfs
B> BIOS + GPT 時，GRUB 通常需要 **BIOS Boot Partition** 放 core.img（和 ESP 是不同的東西）
?ord GRUB 2 在 BIOS 模式下的執行順序：
> BIOS 讀取磁碟最前面的開機碼
> GRUB boot.img
> GRUB core.img（載入模組、找設定）
> GRUB menu 載入 kernel 與 initramfs
E> boot.img 很小，只負責跳到 core.img。
?mc BIOS + GPT 的磁碟上，GRUB 的 core.img 通常放在哪裡？
+ BIOS Boot Partition
- EFI System Partition（ESP）
- /boot/efi
- swap 分割區
E> ESP 是 UEFI 用的；BIOS + GPT 需要另外一個小的 BIOS Boot Partition。
?fill GRUB 2 在 BIOS 模式下，由 boot.img 把控制權交給 ＿＿.img
= core
E> core.img 再載入 modules 並找到 GRUB 設定。

@CARD boot.files | Debian 開機相關檔案

B> **/boot/initrd.img-<ver>**：early user-space image（initramfs）
B> **/boot/grub/grub.cfg**：**自動產生**的 GRUB 選單設定
B> **/etc/default/grub**：管理員的 GRUB 設定
B> **/etc/grub.d/**：產生選單用的腳本
B> kernel 與 initramfs 版本要一致；保留一個已知可用的 kernel 以便救援
?mt 配對檔案與用途：
> /boot/vmlinuz-<ver> :: Linux kernel image
> /boot/initrd.img-<ver> :: early user-space image
> /boot/grub/grub.cfg :: 自動產生的 GRUB 選單
> /etc/default/grub :: 管理員修改的 GRUB 設定
E> 想改 GRUB 設定改 /etc/default/grub，再 update-grub。
?mc 想永久修改 kernel 開機參數，應該編輯哪個檔案，再執行 update-grub？
+ /etc/default/grub
- /boot/grub/grub.cfg
- /boot/vmlinuz
- /etc/grub.d/README
E> grub.cfg 是自動產生的，直接改會在下次 update-grub 時被覆蓋。
?tf /boot/grub/grub.cfg 是自動產生的檔案，不應該手動編輯。
=T
E> 它由 /etc/default/grub 與 /etc/grub.d/ 的腳本產生。

@CARD boot.grubcfg | GRUB 設定與 update-grub
A> 改菜單的正確方式：在「需求單」/etc/default/grub 寫好，叫印刷廠 update-grub 重印 grub.cfg。直接在印好的菜單上塗改，下次重印就不見了。grub-install 則是「重新安裝整台點菜機」，不是改菜單。
B> 編輯 **/etc/default/grub** 與 /etc/grub.d/（例：GRUB_TIMEOUT=5、GRUB_CMDLINE_LINUX_DEFAULT="quiet"）
B> **sudo update-grub** 重新產生 /boot/grub/grub.cfg
B> **不要**為了持久變更去編輯產生出來的 grub.cfg
B> kernel 參數不是 systemd service 設定
B> **update-grub 重新產生選單**；**grub-install 安裝 loader 程式碼**，只用在確認過的開機路徑
?cmd 修改 /etc/default/grub 後，重新產生 GRUB 選單：
= update-grub
= grub-mkconfig -o /boot/grub/grub.cfg
E> Debian 用 update-grub（底層是 grub-mkconfig）。
?mc 想讓 GRUB 選單等待 10 秒，正確做法是？
+ 改 /etc/default/grub 的 GRUB_TIMEOUT=10，再執行 update-grub
- 直接修改 /boot/grub/grub.cfg 中的 set timeout=10，存檔即可生效
- 執行 grub-install --timeout=10，讓設定寫入磁碟的開機磁區
- 修改 /etc/systemd/system.conf 的 DefaultTimeoutStartSec=10s
E> grub.cfg 會被重新產生覆蓋。

@CARD boot.uefi | Debian UEFI 開機
A> Secure Boot 像「層層驗證身分」：firmware 只信任有簽章的 shim，shim 再驗證 GRUB，GRUB 再載入 kernel 和 initramfs。
B> Firmware 從 **ESP** 選 EFI loader
B> **Secure Boot**：**shim** 驗證下一個 loader；GRUB 載入 kernel 與 initramfs
B> amd64 上 EFI/debian 通常有 **shimx64.efi** 與 **grubx64.efi**
B> **/boot/efi** 是 Debian 慣用的 ESP 掛載點
B> 檢查：lsblk -f、findmnt /boot/efi、**efibootmgr -v**（列出 firmware 開機項目）
?cmd 列出 UEFI firmware 中的開機項目（詳細）：
= efibootmgr -v
= efibootmgr
E> efibootmgr 管理 UEFI NVRAM 開機項目與 BootOrder。
?fill Debian 慣用把 ESP 掛載在 /boot/＿＿

@CARD boot.multiboot | 多重開機與修復
A> 修開機像修車：先確認車型（BIOS 還是 UEFI、磁碟配置、root 在哪、有沒有加密），再檢查零件（EFI 項目、ESP 檔案），先試另一把備用鑰匙（舊 kernel），最後才拆引擎（重裝 loader）。
B> 先確認：**BIOS 或 UEFI**、磁碟配置、root filesystem、加密
B> 檢查 EFI 項目與 ESP 檔案，或 BIOS GRUB embedding 區
B> 重裝 loader 前，先在 GRUB 選單試**已知可用的 kernel**
B> 用 Debian installer **rescue mode** 或 live media 修復；掛上實際的 root、/boot、ESP
B> 更新選單（update-grub）**不能**修好所有 loader 故障
?sa Koji 使用 Linux 和 Windows dual boot 一段時間。某次 Windows 強制更新後，他每次開機都在黑畫面後直接進入 UEFI 設定介面，看不到 boot manager 也沒有 emergency shell。請推斷 Windows 更新時可能做了什麼，並提出合理解釋。
S> 2025 期末 Q14
R> 推斷：Windows 更新時改動了 UEFI 開機設定，例如刪除或覆寫了 NVRAM 中 Linux（debian / shim / GRUB）的開機項目、修改 BootOrder，或覆寫 / 清掉 ESP 上的 EFI/debian（shimx64.efi、grubx64.efi）或 fallback 的 EFI/Boot/bootx64.efi，甚至重建 / 重新格式化了 ESP。
R> 解釋：UEFI firmware 開機時要依 NVRAM 的開機項目到 ESP 載入 .efi 程式；如果項目不存在或指向的檔案不見，firmware 找不到任何有效的 boot loader，就只能停在 UEFI 設定介面。因為 GRUB 根本沒被載入，所以不會出現 boot manager 選單，也到不了 kernel / emergency shell（那是更後面的階段）。
R> 修復：用 live / rescue media 開機，掛上 root 與 ESP，以 efibootmgr 重建開機項目或 grub-install 重新安裝 loader。
P> Windows 更改 / 刪除了 UEFI 開機項目（NVRAM BootOrder）或覆寫 ESP 上的 loader
P> firmware 找不到可執行的 EFI loader，所以進入 UEFI 設定
P> GRUB 未載入 → 沒有選單、也沒有 emergency shell（失敗在 firmware 層）
?mc 開機 loader 壞掉需要修復時，在重裝 loader「之前」應該先確認什麼？
+ 是 BIOS 還是 UEFI 開機
- root 檔案系統的使用率
- 螢幕解析度與顯示卡驅動是否相容
- 使用者預設的 shell
E> 這台機器是 BIOS 還是 UEFI 開機，以及磁碟配置與 root 檔案系統的位置。修錯模式（例如在 UEFI 機器上裝 BIOS 版 GRUB）只會讓情況更糟。
?tf 只要執行 update-grub，就能修好所有 boot loader 的故障。
=F
E> update-grub 只更新選單；loader 本身或 EFI 開機項目壞掉要另外修復。

@CARD boot.initramfs | Kernel 與 initramfs
A> initramfs 是「先遣部隊」：真正的 root filesystem 可能被鎖在加密箱（LUKS）、或藏在 LVM 倉庫裡，kernel 自己打不開；所以先派一個小小的臨時檔案系統，裡面帶好驅動和工具，把 root 解鎖、組裝、掛好，再把棒子交給 systemd (PID 1)。
B> **vmlinuz**：初始化 kernel 與內建驅動
B> **initrd.img（initramfs）**：準備儲存裝置並**掛載真正的 root filesystem**
B> early user space 可以：載入驅動、**解鎖加密儲存（LUKS）**、**啟用 LVM**
B> root handoff 之後，**systemd 以 PID 1 執行**
B> initramfs-tools（update-initramfs）與 dracut 的設定不同；重建前先確認產生器
B> 雞生蛋問題：kernel modules 放在 /lib/modules（在 root fs 上），若掛 root 需要的驅動不在 kernel 裡，就**必須放進 initramfs**
?mc 為什麼 root filesystem 在 LVM 或 LUKS 加密磁碟上時，需要 initramfs？
+ 掛載 root 前要先載入驅動、解鎖、啟用 LV，這些工具不能放在還沒掛載的 root 上
- 因為 systemd 只能從 initramfs 啟動，root 上的那份 systemd 只是給救援模式用的備份
- 因為 systemd 只能從 initramfs 啟動，root 上的 systemd 是備用的
- 因為 kernel 本身不認得任何檔案系統，所有 ext4 驅動都只放在 initramfs 裡面
E> early user space 負責解鎖與啟用 LVM，再掛載真正的 root。
?sa LVVM 是一個運作原理類似 LVM 的 kernel device-mapper framework。若系統的 rootfs 在 LVVM partition 上，相比於直接在一般 GPT partition 上，需要額外做哪些設定？LVVM driver 需要在哪個 booting stage 被載入？為什麼？
S> 2025 期末 Q16
R> 額外設定：① 把 LVVM 的 kernel module 與使用者空間工具（啟用 volume 的指令）加入 initramfs，並在 initramfs 中於掛載 root 前啟用 LVVM volume（類似 LVM 的 vgchange -ay），之後重建 initramfs（update-initramfs -u）；② kernel command line 的 root= 指向 LVVM 的 device mapper 路徑（如 /dev/mapper/...），/etc/fstab 也要對應；③ boot loader 可能無法讀取 LVVM，所以 /boot（kernel 與 initramfs）通常要放在一般 partition 上（UEFI 的 ESP 也要是一般 FAT partition）。
R> 載入階段：必須在 kernel 掛載 root filesystem 之前，也就是 initramfs（early user space）階段，或直接編進 kernel。原因：一般 kernel module 存放在 root filesystem 的 /lib/modules，但 root 本身就在 LVVM 上，沒有 driver 就無法掛載 root，形成雞生蛋問題；所以 driver 必須由 initramfs 提供（或 built-in），等到 systemd（PID 1）才載入就太晚了。
P> initramfs 需包含 LVVM driver 與工具並啟用 volume，重建 initramfs
P> root= / fstab 指向 LVVM 裝置；/boot 放在一般 partition
P> 在 initramfs（掛 root 之前）載入
P> 原因：modules 在 root fs 上，雞生蛋問題
?cmd 在 Debian（initramfs-tools）重建目前 kernel 的 initramfs：
= update-initramfs -u
= update-initramfs -u -k $(uname -r)
= update-initramfs -u -k all
E> -u 更新、-k 指定 kernel 版本。

@CARD boot.pid1 | PID 1 與 kernel threads
A> PID 1 是「這棟大樓的總管」：所有 user-space 服務都由它啟動、它負責看顧；父母先走的孤兒 process 也由它收養。kernel threads（如 kthreadd）則是 kernel 自己的工作人員。
B> Debian：PID 1 是 **systemd**；kernel tasks 如 **kthreadd**
B> FreeBSD：PID 1 是 **init**
B> PID 1 啟動 / 監管 user space，並**處理 orphaned processes**
B> kernel task 名稱與 PID 會因版本改變 → 理解 PID 1 的角色，而不是死背 PID 列表
X> ps -p 1 -o pid,comm
?cmd 查看 PID 1 是什麼程式（顯示 pid 與指令名稱）：
= ps -p 1 -o pid,comm
= ps -o pid,comm -p 1
E> -p 選 PID、-o 選欄位。
?mc 一個 process 的父 process 先結束了（成為 orphan），之後由誰接手？
+ PID 1（或指定的 subreaper）
- kernel thread kthreadd
- 它的子 process
- 沒有人，它會立刻被殺掉
E> PID 1 會處理 orphaned processes，負責在它們結束後 reap。
?mt 配對系統與 PID 1：
> Debian :: systemd
> FreeBSD :: init
E> PID 1 的角色相同：啟動並監管 user space。

@CARD boot.systemctl | systemctl：start vs enable
A> start 是「現在開燈」，enable 是「設定每天回家自動開燈」。兩件事獨立：開了燈不代表明天會自動開；設定了自動開燈也不會讓現在的燈亮，除非加 --now。

B> **enable** 設定**開機時**（或透過依賴）啟動的策略

@CARD boot.units | Unit 類型與依賴

@CARD boot.defdeps | 預設依賴：Conflicts=shutdown.target

P> Before：在 shutdown.target 之前完成停止（順序）

@CARD boot.shutdown | 有序關機與關機指令
A> 有序關機像打烊：先通知客人、各部門收工（停服務）、把帳本寫好（flush、unmount）、最後關燈或關電源。halt 是「停止營業但電燈沒關」、poweroff 是「關掉總電源」、reboot 是「打烊後重新開店」。
B> 通知使用者 → 停止服務、終止剩餘 process → flush 寫入、unmount → halt / poweroff / reboot
B> **sync 不能取代**有序關機
B> **Halt**：停止執行，**電源可能仍開著**（systemctl halt）
B> **Poweroff**：停止並要求斷電（systemctl poweroff）
B> **Reboot**：停止並重啟（systemctl reboot）
B> **shutdown -r +10 "Maintenance"**：10 分鐘後重開；**now** 立即；**shutdown -c** 取消
B> Debian systemd 的 **shutdown -h** 通常是 poweroff；**FreeBSD shutdown -h 是 halt、-p 是 poweroff**

@CARD boot.disaster | dd 誤寫磁碟開頭：MBR vs GPT
A> MBR 把分割表寫在「唯一一張」紙條上，撕掉就沒了；GPT 在磁碟開頭和結尾各放一份（主表 + 備份），開頭被毀還能用尾巴那份救回來。
B> GPT 佈局：LBA 0 = protective MBR、LBA 1 = **primary GPT header**、LBA 2-33 = partition entries；磁碟**最後**還有 **backup GPT header + entries**
B> dd 從 /dev/sda 開頭寫掉 40KB：MBR（boot code + 分割表）或 GPT 主 header 與主分割表都會被毀；partition 通常從 1MiB 開始，所以 filesystem 本身可能完好
B> 執行中的系統：kernel 已在記憶體中讀好分割表，可能還能跑；**重開機才是問題**
B> **MBR**：boot code 與唯一一份分割表都沒了 → BIOS 無法開機、kernel 找不到 partition；只能靠事先備份（sfdisk -d）或 testdisk 掃描重建
B> **GPT**：主表毀，但可用磁碟尾端的**備份 GPT** 恢復（gdisk / sgdisk），部分 UEFI firmware 也會自動用備份 → 災難復原容易得多
?sa 培根要用 dd 清空 USB（/dev/sdc），卻打成 rootfs 所在的 /dev/sda，按 Ctrl+C 時已有 10 個 block（40KB）被清掉。假設 root filesystem 與 system files 沒被清掉，這台工作站還有辦法重開機嗎？為什麼？在這種情況下 MBR 與 GPT 在災難復原的考量上有什麼差別？
S> 2025 期末 Q15
R> 磁碟開頭 40KB 存放的是分割資訊與開機資料：MBR 的 boot code 與 partition table（sector 0），或 GPT 的 protective MBR、primary GPT header（LBA 1）與 partition entry array（LBA 2-33，約 16KB）。這些都被清掉了。
R> 目前系統因為 kernel 已在記憶體中載入分割表，可能還能繼續執行，但「直接重開機」很可能無法開機：BIOS/MBR 情況下 boot code 不見，firmware 無法開機；即使能載入 loader，也讀不到分割表找不到 root / ESP。所以應在重開機前先修復分割表。
R> MBR vs GPT：MBR 只有一份分割表、沒有備份，被覆蓋後只能靠事先的備份（sfdisk -d）或用 testdisk 等工具掃描磁碟猜回分割位置，風險高。GPT 在磁碟最後有 backup GPT header 與 partition entries，可以用 gdisk / sgdisk 從備份重建主表（部分 UEFI firmware 也能自動使用備份），災難復原容易很多；之後再重建 protective MBR 或重新 grub-install / 確認 ESP。
P> 被清掉的是 MBR / GPT header 與分割表（+ BIOS boot code）
P> 重開機會失敗（找不到 boot code / 分割資訊），執行中系統暫時可運作
P> MBR 無備份，只能事前備份或掃描重建
P> GPT 有磁碟尾端的 backup header / table 可復原
?fill GPT 的備份 header 與 partition entries 存放在磁碟的＿＿（開頭/結尾）
= 結尾
= 尾端
= 最後
= 末端
E> 主表在開頭，備份在結尾。

@CARD boot.p_unit | 實作：寫一個可靠的 service unit
A> systemd 是「會幫你顧小孩的保母」：你只要寫一個一直在前景跑的程式，背景化、重啟、收 log、關機時叫它停，全部交給保母。最常見的錯就是自己在腳本裡加 & 或 nohup 把程式丟到背景，保母以為小孩不見了。
B> **Type=simple**（預設）：ExecStart 的程式要**留在前景**一直跑，不要自己 fork 到背景
B> **ExecStart 必須是絕對路徑**；指令裡要用 pipe 或變數展開得包一層 `/bin/sh -c '...'`
B> **Restart=on-failure** 加 **RestartSec=2**：異常結束自動重啟
B> 程式的 stdout / stderr 自動進 journal（journalctl -u 看得到）；Python 等有輸出緩衝的語言要關掉緩衝（`python3 -u` 或 `Environment=PYTHONUNBUFFERED=1`），不然 log 會延遲很久才出現
B> **After=** 只管順序、**Wants= / Requires=** 才是依賴；需要某掛載點先就緒：**RequiresMountsFor=/mnt/hw2/sftp**
B> **[Install] WantedBy=multi-user.target** 才能 enable；放在 **/etc/systemd/system/**
X> [Unit]
X> Description=SFTP upload watcher
X> RequiresMountsFor=/mnt/hw2/sftp
X> [Service]
X> Type=simple
X> ExecStart=/usr/local/bin/sftp_watchd
X> Restart=on-failure
X> RestartSec=2
X> [Install]
X> WantedBy=multi-user.target
?mc 把一個 shell script 做成 Type=simple 的 service，腳本最後一行寫成 `main_loop &` 就結束。會發生什麼事？
+ 主程序馬上結束，systemd 認為服務已停止（並依設定清掉殘留的背景程序）
- 服務正常運作，只是 MainPID 指向背景的程序
- systemd 偵測到背景程序，會自動改用 Type=forking
- systemd 會等背景程序結束後才把服務標成 active，所以開機一直卡住
E> Type=simple 要求 ExecStart 啟動的那個程序就是服務本身，必須留在前景。
?mc Python 寫的 daemon 用 print 輸出訊息，但 `journalctl -u` 很久才看到 log，或停止服務時才一次出現。原因？
+ stdout 被緩衝，要關閉緩衝
- journald 每小時才寫入一次
- 沒有設定 SyslogIdentifier
- 沒有 enable 服務
E> stdout 不是終端機時會被整塊緩衝；要用 -u 或 PYTHONUNBUFFERED 關閉緩衝。也可以在 print 加 flush=True。
?fill 希望 service 在 /mnt/hw2/sftp 這個掛載點就緒之後才啟動，可以在 [Unit] 寫 ＿＿=/mnt/hw2/sftp
= RequiresMountsFor
E> systemd 會自動加上對應 .mount unit 的 Requires 與 After。
?tf unit 檔的 ExecStart= 可以直接寫 `sftp_watchd`，systemd 會用 PATH 幫忙找。
=F
E> 傳統上必須寫絕對路徑；請一律寫完整路徑，最不會出錯。

@CARD boot.p_luks | 實作：LUKS 與 cryptsetup
A> LUKS 加密碟像「有 8 個鑰匙孔的保險箱」：真正加密資料的 master key 只有一把，但每個鑰匙孔（key slot）可以各設一組密碼，任何一組都開得了。所以換密碼不必重新加密整顆碟，只是換掉某個鑰匙孔。
B> 堆疊順序（由下而上）：分割區 → **LUKS** → /dev/mapper/名稱 → LVM PV → LV → 檔案系統；`lsblk` 的 TYPE 欄會顯示 **crypt**
B> 看標頭與 key slot：**cryptsetup luksDump 裝置**
B> 換密碼：**cryptsetup luksChangeKey 裝置**（先問舊的再問新的）；加一組：**luksAddKey**；移除：**luksRemoveKey**
B> 開 / 關：**cryptsetup open 裝置 名稱**、**cryptsetup close 名稱**
B> 開機時自動解鎖的對照表：**/etc/crypttab**（名稱、來源裝置、金鑰檔或 none、選項），改完要 update-initramfs -u
B> 換完密碼務必重開機實測；最好先 luksAddKey 加新的、確認能用，再刪舊的
X> lsblk -o NAME,TYPE,FSTYPE,MOUNTPOINT
X> cryptsetup luksDump /dev/sda3 | grep -i slot
X> cryptsetup luksChangeKey /dev/sda3
X> cat /etc/crypttab      # sda3_crypt UUID=... none luks
?mc 為什麼更改 LUKS 密碼幾乎瞬間完成，不需要把整顆磁碟重新加密？
+ 密碼只保護 master key
- 因為 LUKS 其實沒有加密資料
- 因為新密碼要等到下次開機才生效
- 因為只加密了檔案名稱
E> 密碼只用來保護 key slot 裡的 master key；資料是用 master key 加密的，master key 沒變。這也是為什麼可以同時存在多組密碼。
?mt 配對 cryptsetup 子指令：
> luksDump :: 顯示 LUKS 標頭與 key slot 資訊
> luksChangeKey :: 把某組舊密碼換成新密碼
> luksAddKey :: 在空的 key slot 新增一組密碼
> open :: 解鎖並建立 /dev/mapper 下的裝置
E> 加與換都需要先提供一組現有的有效密碼。
?ord 一個典型加密系統的儲存堆疊，由最底層到最上層：
> 磁碟分割區（/dev/sda3）
> LUKS 加密層（/dev/mapper/sda3_crypt）
> LVM（PV → VG → LV）
> 檔案系統（ext4）
E> 所以開機要先解鎖 LUKS，才看得到裡面的 LVM。
?fill 記錄「開機時要解鎖哪些加密裝置」的設定檔是 /etc/＿＿
= crypttab
E> 格式：名稱、來源裝置、金鑰檔（none 表示詢問密碼）、選項。

@CARD boot.p_target | 實作：卡在 rescue / emergency 怎麼出來
A> 每次開機都掉進 rescue，像「車子每次發動都自動開進維修廠」。原因只有幾種：預設目的地被設成維修廠（default target）、有人在開機參數寫死了目的地、或是路上真的壞了（fstab 掛不起來會掉進 emergency）。先分辨是哪一種。
B> 查預設：**systemctl get-default**；改回來：**systemctl set-default multi-user.target**（其實是改 /etc/systemd/system/default.target 這個 symlink）
B> 不重開機直接切換：**systemctl isolate multi-user.target**，或 **systemctl default**
B> 預設值正常卻還是進 rescue：看 **/proc/cmdline** 有沒有 systemd.unit=rescue.target 或 single，源頭在 /etc/default/grub，改完 update-grub
B> **emergency** 模式通常是 fstab 某一行掛載失敗：`journalctl -xb` 找原因，非必要的掛載加 **nofail**
B> rescue 與 emergency 的差別：rescue 會掛載本機檔案系統並啟動基本服務；emergency 只有唯讀的 root 和一個 shell
X> systemctl get-default
X> ls -l /etc/systemd/system/default.target
X> cat /proc/cmdline
X> systemctl set-default multi-user.target && systemctl isolate multi-user.target
?cmd 查詢系統目前的預設開機 target：
= systemctl get-default
E> 結果應該是 multi-user.target 或 graphical.target。
?mc `systemctl get-default` 顯示 multi-user.target，但每次開機仍然進入 rescue mode。接下來最該檢查什麼？
+ 看 /proc/cmdline 的 kernel 參數
- /etc/passwd 的 root shell
- /etc/hostname
- 記憶體大小
E> cat /proc/cmdline，看 kernel 參數有沒有指定 systemd.unit=rescue.target。kernel 命令列的 systemd.unit= 會蓋過 default.target，源頭通常在 /etc/default/grub。
?cmd 不重開機，立刻從 rescue 切換到 multi-user.target：
= systemctl isolate multi-user.target
= systemctl default
E> isolate 會啟動目標 target 需要的 unit，並停掉不屬於它的。
?mc 在 /etc/fstab 新增一行掛載，但裝置路徑打錯了。下次開機最可能的結果？
+ 等待逾時後進入 emergency mode
- 系統會忽略那一行，照常完成開機
- GRUB 的開機選單會消失
- kernel 找不到 root 而 panic
E> 沒有 nofail 的掛載被視為必要，失敗就會掉進 emergency。
